## Summary

This is a well-built plugin and the review found nothing that threatens the
design. INV-1 through INV-9 hold on every path I traced, and several of them
are enforced *structurally* rather than by discipline — `MatrixScope` is the one
place that can build the pair predicate, `TransitionMapQuery#population` cannot
produce a relation on `workflows` without naming a `project_id`, and
`ScopeWriter` keeps the three actions of INV-3 as three methods that cannot
collapse into one another. Security holds up: every raw SQL value passes through
`Integer()` or `connection.quote`, and every id from a request is intersected
with a list the server built rather than handed to a `where`, which is the
stronger of the two habits.

The most valuable thing I can report is a negative: I re-walked Redmine's source
myself for all three supported versions, and the integration-points table in
`docs/design.md` is complete and accurate. That table is the plugin's real
safety argument, and it holds.

What I did find is nine edges. One matters: an administration matrix saved with
**All** projects selected quietly turns that selection into an explicit list of
every project id, which then rides in the redirect URL and in every action link
afterwards — on a large installation that is an 8–10 KB URL and a 414 (F01).
The repository already knows this shape is dangerous; there is a spec asserting
that the scope-panel links keep `all` as `all`, and the Save form's hidden fields
do the opposite a few files away. Two more are worth a fixer's time: a copy into
a project can leave a scope standing with no rules left in it, which for
transitions is the frozen-project state ADR-001 exists to keep unreachable by
accident (F03), and `.rubocop.yml` declares `TargetRailsVersion: 8.1` — the
*newest* supported host rather than the oldest — so the lint gate is pointed the
wrong way for a plugin that has to run on Rails 6.1 (F02).

Nothing here is a blocker and nothing needs an ADR.

**Counts:** blocker 0 · major 1 · minor 4 · nit 3 · question 1

### F01 — "All projects" is expanded into an explicit id list by the Save form, so the redirect URL grows with the number of projects

- **Status:** fixed
- **Severity:** major
- **Confidence:** confirmed
- **Category:** operability
- **Where:** `lib/redmine_project_workflows/overrides/workflows_edit_add_project_hidden_field.rb`,
  `lib/redmine_project_workflows/overrides/workflows_permissions_add_project_hidden_field.rb`,
  `lib/redmine_project_workflows/patches/workflows_controller_project_selection.rb:117`
  (`selected_project_param_values`), `lib/redmine_project_workflows/patches/workflows_controller_patch.rb:72`
  and `:116`
- **Invariant touched:** none

**What is wrong**

The repository holds two opposite positions on the `all` keyword, four files
apart. `app/views/redmine_project_workflows/_scope_panel.html.erb:19` keeps it
verbatim — *"'all' stays 'all': expanding it would put every project id in the
link"* — and `spec/integration/deface_overrides_spec.rb:143` asserts that it
does. The two hidden-field overrides on the **Save** form do the opposite:

```erb
<% if project_ids.include?('all') %>
  <% project_ids = @projects.map { |project| project.id.to_s } + ['global'] %>
<% end %>
```

The selector and the matrix are two separate forms in core's `workflows/edit`
(the selector is a GET form ending at `submit_tag l(:button_edit)`; the matrix
is the PATCH form around `div.autoscroll`), so the hidden fields are the only
thing that carries the selection into the save — and they carry it expanded.
After that save, `load_project_options` sees no `all`, `@all_selected` is
`false`, and it stays false for the rest of the session.

**Why it matters**

An administrator on an installation with 500 projects selects **All** in the
project selector, changes one cell of the transitions matrix and presses Save.
The write itself is correct. Then `update` redirects to

```ruby
edit_workflows_path(project_id: selected_project_param_values, …)
```

which is now `['global', id1, …, id500]` — roughly 11 KB of query string in a
302 `Location` header. nginx's default `large_client_header_buffers` is 8 KB, so
the follow-up GET is rejected: the save succeeded and the administrator sees a
414. Below that threshold the failure is quieter: the selection is no longer
`all`, so every one of the four scope-action links on the re-rendered page
carries the same 500 ids, the page grows by tens of kilobytes, and pressing
*Give own workflow* fails the same way.

No spec drives `update` or `update_permissions` with `project_id: ['all']` —
`['all']` appears in the suite only on `get :edit` and in `duplicate_with_target`
— so nothing in CI would notice.

**How I verified it**

Read-only, not executed, but traced against real core source rather than from
memory: I cloned `5.1-stable`, `6.1-stable` and `7.0-stable` and confirmed that
`workflows/edit.html.erb` and `workflows/permissions.html.erb` really do put the
project selector and the matrix in two separate `form_tag` blocks in all three,
which is what makes the hidden fields load-bearing. The rest is the code path
above, read end to end: override → `load_project_options` (`@all_selected =
project_ids.delete('all').present?`) → `selected_project_param_values` →
`redirect_to`. I did **not** measure a real 414; the URL length is arithmetic on
`Project.count`, and the threshold is nginx's documented default.

**Suggested direction**

Make the hidden fields agree with the action links: when the submitted selection
is `all`, emit one `hidden_field_tag 'project_id[]', 'all'` and let
`load_project_options` expand it server-side, which it already does. If the
expansion is deliberate — pinning the selection against a project created
between page load and save is the only reason I can construct — then that reason
belongs in a comment and in `docs/DECISIONS.md`, because the code currently
reads as the two overrides not knowing about the spec four files away. Either
way the gap the fixer should close is the missing example: `update` with
`project_id: ['all']`, asserting what the redirect carries.

**Resolution:** confirmed, then fixed. The two
Deface overrides now emit one `hidden_field_tag 'project_id[]', 'all'` and let
`load_project_options` expand the keyword server-side, which it already did; the
write population is identical (`@all_selected` makes `@global_selected` true and
`@selected_projects` every project), and the redirect and every action link now
carry `all`. **Red on the old code:** two new examples in
`spec/integration/deface_overrides_spec.rb` render `workflows/edit` and
`workflows/permissions` with `project_id: ['all']` and read the hidden inputs of
the matrix form; on `c3047cf` both failed with
`expected: ["all"] got: ["1", "5", "6", "3", "4", "2", "global"]`, which is the
expansion this finding describes. The missing coverage the finding asks for is in
as well, as `describe 'saving the whole-installation selection'` in
`spec/controllers/workflows_controller_spec.rb`: `update` and `update_permissions`
with `project_id: ['all']`, asserting that every project *and* the generic
workflow were written and that the redirect carries the keyword. Those two are
**green on the old code** and stated as such — the expansion happened in the
form, so a controller driven with `['all']` directly always behaved correctly.
One side effect worth knowing: on an installation with exactly one project the
expanded form set `@project` and changed the layout; `all` does not, and
`load_project_options` says in a comment that it should not.

### F02 — `.rubocop.yml` declares the newest supported Rails, not the oldest, so the lint gate points the wrong way

- **Status:** fixed
- **Severity:** minor
- **Confidence:** confirmed
- **Category:** build
- **Where:** `.rubocop.yml:16` (`TargetRailsVersion: 8.1`)
- **Invariant touched:** none

**What is wrong**

The three supported hosts do not run the same Rails: Redmine 5.1 pins
`rails 6.1.7.10`, 6.1 pins `7.2.3.2`, 7.0 pins `8.1.3.1`. `TargetRailsVersion`
tells RuboCop which Rails APIs it may *require*, so setting it to 8.1 configures
the gate for the newest host the plugin supports rather than the oldest one it
has to run on. `TargetRubyVersion` two lines above is already set to the minimum
(3.2, which is what CI uses for 5.1); this is the same decision made the other
way round.

**Why it matters**

A contributor writes `params.require(:workflow).permit(…)` in a future
controller. RuboCop with `TargetRailsVersion: 8.1` enables
`Rails/StrongParametersExpect`, which demands `params.expect(…)` — a method that
does not exist before Rails 8.0. The contributor complies, RuboCop goes green,
the lint job goes green, and the plugin raises `NoMethodError` on Redmine 5.1
and 6.1. The same shape applies to `Rails/EnumSyntax` (7.0+) and every other
version-gated cop. The failure mode is specifically that *the gate approves it*,
which is worse than the gate being absent.

**How I verified it**

`grep "gem 'rails'" Gemfile` in each of the three checkouts, which printed the
three versions above. Then I grepped `app/`, `lib/` and `init.rb` for the
Rails-7-and-later APIs such a cop would push toward — `params.expect`,
`.intersect?`, `.excluding`, `.in_order_of`, `.sole`, `.pick`, `Data.define` —
and found none. So this is latent: nothing in the tree is broken by it today,
and I ran RuboCop with the repository's own bundle to confirm the current
config is clean (92 files, no offences).

**Suggested direction**

`TargetRailsVersion: 6.1`, matching `TargetRubyVersion`'s existing logic, with a
one-line comment saying that it tracks the *oldest* supported host and why. The
comment matters more than the value: the current setting reads like it was
chosen to match Redmine 7.0's own configuration, which is a defensible thing to
have wanted and the wrong answer for a plugin spanning three hosts.

**Resolution:** confirmed, then
fixed. `TargetRailsVersion: 6.1`, with the reasoning in a comment beside it.
**Red on the old code:** a new example in `spec/plugin_conventions_spec.rb`
asserts that the configured target is not newer than the Rails of the host the
suite is running in. With `8.1` it fails on the 5.1 cell —
*".rubocop.yml targets Rails 8.1; this host runs 6.1.7.10, so the lint gate can
approve code this host cannot run"* — and passes on 7.0 either way, which is
exactly the property: the value has to be true of every supported host, and the
oldest cell is what enforces it. RuboCop through `.github/lint/Gemfile` is clean
at 6.1 (96 files, no offences) and no `.rubocop_todo.yml` entry was added.

### F03 — a copy into a project can leave an existing scope standing with no rules in it

- **Status:** fixed
- **Severity:** minor
- **Confidence:** probable
- **Category:** correctness
- **Where:** `lib/redmine_project_workflows/patches/workflow_rule_patch.rb:23`
  (`copy_for_project`), `lib/redmine_project_workflows/services/scope_writer.rb:73`
  (`ensure_scopes_for_existing_rules`), `lib/redmine_project_workflows/patches/workflows_controller_patch.rb:303`
  (`record_scopes_for_copy`)
- **Invariant touched:** INV-3 — not violated, but the state it makes reachable
  is the one ADR-001 wants unreachable by accident

**What is wrong**

`ensure_scopes_for_existing_rules` is careful in one direction and silent in the
other. It refuses to *create* a scope where the copy left no rules, and its
comment says exactly why: *"creating a scope where nothing was copied would hand
the project an empty workflow, which for transitions means no issue in it can
change status."* But `copy_for_project` deletes the target's rows for the copied
(tracker, role) pairs across **both** rule types before inserting, and nothing
looks at what happens to a scope that was **already there**. If the source has
no rules of one type for that pair, the target keeps its scope and loses every
rule of that type.

**Why it matters**

Project P runs its own transitions workflow for (Bug, Developer) — scope plus
rules. An administrator opens **Administration → Workflow → Copy**, picks a
source (tracker, role) pair whose generic workflow happens to have field
permissions but no transitions, and targets P / Bug / Developer. `copy_for_project`
deletes P's rows for that pair, inserts the source's field permissions, and
inserts no transitions. `record_scopes_for_copy` correctly declines to create a
transitions scope — but P already had one, so it survives with zero rules. P now
has an own **empty** transitions workflow: no issue in P can change status for
Developer. The flash says *Successful update*, and nothing counts or names it.

This is the same defect as R01/R02 of the 0.1.1 review — a screen writing an own
empty workflow that nobody asked for — reached from the copy screen rather than
from Save. Whether the right answer is to refuse, to warn, or to accept it as
the honest meaning of a replacing copy is a judgement; what is missing today is
that the asymmetry is neither documented nor visible.

I have marked this **probable** rather than confirmed because I could not run
it. The reasoning is a read of the two methods, and the case needs a source pair
with rules of one type and none of the other, which is unusual but entirely
reachable — a (tracker, role) whose transitions were never configured.

**How I verified it**

Read-only, not executed. `copy_for_project` → `delete_existing_rules_for_project`
(or `copy_one_for_project`'s own `delete_all` when there is a single pair), both
of which scope by `(tracker_id, role_id, project_id)` with no `type` predicate,
so both rule types go. Then `ensure_scopes_for_copy` → `ensure_scopes_for_existing_rules`,
which only ever calls `create_scopes` and never removes one. I did not find a
spec in `spec/models/workflow_rule_copy_spec.rb` covering a target that already
held a scope of a type the source has no rules for, but I read that file's
example names rather than the file in full, so treat that as unconfirmed too.

**Suggested direction**

Decide what a replacing copy means for a scope it emptied, then make the code
and the message say the same thing. The cheapest honest version is to count
them and report: `record_scopes_for_copy` already knows the targeted triples and
`ScopeState` can already tell `own` from `own_empty`, so "N combinations now
have an own empty workflow" is a query it is a short step from making. Refusing
outright is the other option and is a bigger behaviour change than it looks —
the copy is also how somebody deliberately empties a project.

**Resolution:** confirmed by
running it, then fixed as the finding's cheaper option — counted and reported,
not refused. `WorkflowsController#duplicate` now asks
`ScopeCombinations.own_empty_count` about the combinations the copy actually
acted on and adds a warning naming them (`notice_project_workflow_copy_left_empty`,
pluralised, added and translated in all eight locale files). Refusing was
rejected for the reason the finding gives: the copy is also how somebody
deliberately empties a project, so refusing is a behaviour change and reporting
is not. **Red on the old code:** *"says when the copy left a combination with its
own empty workflow"* in `spec/controllers/workflows_controller_spec.rb` copies a
source pair that has field permissions and no transitions into a project that
owns its transitions, and asserts `flash[:warning]`; on `c3047cf` it failed with
`got: nil`. The same example's other two assertions — the scope survives, and it
is now empty — passed on the old code, which is the defect state the finding
describes. A second example asserts nothing is said when every targeted
combination still has rules.

### F04 — the copy path's audit stamp covers combinations whose rules it did not touch

- **Status:** adjusted
- **Severity:** nit
- **Confidence:** confirmed
- **Category:** correctness
- **Where:** `lib/redmine_project_workflows/services/scope_writer.rb:98`
  (`ensure_scopes_for_copy`)
- **Invariant touched:** none

**What is wrong**

`ensure_scopes_for_copy` loops both rule types and, for each, calls
`touch_scopes` with the full cross product of `project_ids × tracker_ids ×
role_ids` — regardless of whether the copy moved any rule of that type. The two
rule writers get the same thing right by construction: their `touch_scopes` set
is `writable_pairs`, which is provably exactly the set of scoped pairs in the
selection, so they can only stamp what they wrote.

**Why it matters**

A copy that moves only transitions still bumps `updated_by_id` and `updated_at`
on the target's **field-permission** scopes. The project's Workflow tab and the
inventory then say *"Updated by Jan 2 minutes ago"* beside a set of field
permissions Jan did not change. WP6 added those columns precisely so that
somebody can ask who last changed a workflow, and this is the one path where the
answer is wrong. It is a nit because nothing acts on the value.

**How I verified it**

Read-only, not executed. `ensure_scopes_for_copy` calls `touch_scopes` outside
any test of whether `ensure_scopes_for_existing_rules` found rules of that type
— its return value (`created`) is collected and the touch runs either way. I
checked the writers' equivalent for the same defect and it is not there: since
`writable_pairs` returns *every* scoped pair of the cross product, the cross
product of its trackers and its roles selects exactly the rows `touch_scopes`
should update, and no others.

**Suggested direction**

Touch per rule type only where that type's copy actually landed something. The
existing plucked set inside `ensure_scopes_for_existing_rules` (`with_rules`)
already names them.

**Resolution:** `adjusted` rather than
`fixed`, because the defect is real and the reasoning behind it was not — and
that difference is what the fix had to be shaped around, so it is worth a
reader's attention rather than a tick. Real, but not for the reason given — and worth stating, because the difference is what the fix had to
be shaped around. The finding says a copy that moves only transitions still
stamps the target's field-permission scopes. It does, and that part of the stamp
is **correct**: `copy_for_project` deletes the target pair's rows across *both*
rule types before inserting (`delete_existing_rules_for_project` and
`copy_one_for_project`'s own `delete_all` both run on `WorkflowRule`, which has
no type predicate), so such a copy has just deleted every field-permission rule
the target had. *"Updated by Jan 2 minutes ago"* beside them is true; Jan wiped
them. What is genuinely wrong is narrower, and reachable: the stamp covered the
cross product of the target trackers and roles, including the pairs
`copy_for_project` **skips** because their source resolves to the target itself.
*Source: any project, any role, this tracker* into that same tracker and role
copies nothing at all, and every combination it named was stamped anyway.
Fixed by making the copy report what it did: `copy_for_project` returns the pairs
it copied, the controller turns those into (project, tracker, role) triples, and
`ScopeWriter.touch_combinations` stamps exactly those triples. `touch_scopes`,
which stamps a cross product, stays for the matrix save, where the cross product
really is what was rewritten. **Red on the old code:** *"does not stamp a
combination the copy skipped"* in
`spec/controllers/workflows_controller_spec.rb` failed with
`expected: nil got: 1`; a companion example asserts that a combination the copy
*did* write is still stamped. Unit-level cover in
`spec/services/scope_writer_spec.rb` (*"stamps exactly the combinations it was
given, not their cross product"*) and in the new
`spec/services/scope_combinations_spec.rb`.

### F05 — a scope for a role the project screen does not list is invisible and unreachable there

- **Status:** fixed
- **Severity:** minor
- **Confidence:** confirmed
- **Category:** ux
- **Where:** `lib/redmine_project_workflows/services/project_options.rb:170`
  (`.roles`), `app/helpers/project_workflows_helper.rb:28`
  (`project_workflow_settings_rows`)
- **Invariant touched:** none

**This does not re-open a decision.** `docs/DECISIONS.md` answered **A** on
2026-08-26: the project screen offers only the roles that have members in the
project, and *Non member* and *Anonymous* are not on it. That decision stands
and this finding does not argue with it. What it reports is that one sentence of
its stated premise does not hold.

**What is wrong**

The decision's reasoning — and the comment in `ProjectOptions.roles`, and the
README — is that those roles *"go on following the generic workflow"*. They do
not have to. The same paragraph of the README says a system administrator can
still give a project its own workflow for them from Administration → Workflow,
and `ProjectWorkflowScopesController` will do it. Once that has happened, the
project has an own workflow that its own Workflow tab neither shows nor can undo:
the rows come from `ProjectOptions.roles`, which requires a `MemberRole`, so
there is no line for it and no *Return to the generic workflow* button.

The same thing happens to an ordinary role: remove the last member holding it
and the project's existing scope for that role drops off the tab while staying
in force.

**Why it matters**

A project manager with `manage_project_workflow` opens **Project settings →
Workflow** to find out why anonymous visitors cannot move issues, and the tab
does not mention the role at all. There is no path from the screen that is meant
to answer that question to the state that causes it — only Administration, which
they do not have. It is a hole in the tab's completeness rather than a wrong
answer: nothing the tab *does* say is untrue.

**How I verified it**

Read-only, not executed. `ProjectOptions.roles` starts from
`MemberRole.joins(:member).where(members: {project_id: …})`, so a role with no
member in the project cannot appear whatever its scopes. `ProjectWorkflowScopesController`
resolves its `role_id` against `Role` with no such restriction, and
`Role#consider_workflow?` in all three checkouts is `has_permission?(:add_issues)
|| has_permission?(:edit_issues)` — nothing about being builtin — so both builtin
roles reach the administration selector whenever they hold either permission.

**Suggested direction**

Keep the decision and widen only the *display*: build the tab's row list as the
roles `ProjectOptions.roles` offers, plus any role that already has a scope for
this project. A row that arrived the second way can be read-only, or offer only
*Return to the generic workflow* — that is the action a project manager needs
and the one the decision does not forbid. The comment in `ProjectOptions.roles`
should stop saying those roles go on following the generic workflow and say
instead that the project screen does not offer to change them.

**Resolution:** confirmed, then
fixed as the finding suggests — the decision of 2026-08-26 stands and only the
display and the undo path widen. `ProjectOptions.visible_roles` is `.roles` plus
every role that already has a scope for this project;
`ProjectWorkflowsController` resolves `@role` against it and records
`@role_offered`. A row that arrived the second way is fully visible, can be
opened, emptied and returned to the generic workflow, and is refused the one
thing the decision does forbid: `require_offered_role` answers **403** for
`#enable`, and the tab renders no *give own workflow* links for it. 403 rather
than 404 because the combination exists and may be looked at; it is the action
that is not on offer. The comment in `ProjectOptions.roles`, the paragraph in
`README.md` and the table in `docs/design.md` no longer say those roles go on
following the generic workflow. **Red on the old code:** four examples — three in
`spec/controllers/project_workflows_controller_spec.rb` (a scoped role with no
member can be opened; can be returned; is refused `#enable`) failing with 404,

### F06 — a save that wrote nothing reports "Successful update"

- **Status:** fixed
- **Severity:** minor
- **Confidence:** confirmed
- **Category:** ux
- **Where:** `lib/redmine_project_workflows/patches/workflows_controller_patch.rb:195`
  (`report_matrix_save`), `lib/redmine_project_workflows/services/transition_writer.rb:44`,
  `lib/redmine_project_workflows/services/permission_writer.rb:31`
- **Invariant touched:** none

**What is wrong**

`report_matrix_save` does not know how many rules were written; it infers it as
`(projects × trackers × roles) − skipped`. But the writers return `0` for
`skipped` in two quite different situations: when they wrote everything, and
when they returned early at `return 0 if transitions.empty?` because the
sanitized payload had nothing left in it. In the second case `written` is the
whole selection and the flash says *Successful update*.

**Why it matters**

The payload can end up empty two ways. The first is every cell left at
*(No change)* — core reports success there too, so that is not a regression and
arguably not wrong. The second is the plugin's own: `sanitize_transitions` and
`sanitize_permissions` **drop** entries that fail the whitelist, and the README
promises that when they do, the entry "leaves the rule it names alone rather
than clearing it". That is the right behaviour and the wrong message — a request
whose every entry was rejected is reported as a successful save of the whole
selection. It takes a hand-built request to get there, which is why this is
minor rather than major, but the whole point of the drop-before-delete rule is
that a rejected value is safe, and telling the operator it was applied undoes
half of that.

**How I verified it**

Read-only, not executed. Traced `replace_transitions_for_project_id` →
`sanitize_transitions` → `return 0 if transitions.empty?` and read
`report_matrix_save`'s arithmetic against it. The `no_change` half I checked
against core's own `update`, which sets `flash[:notice]` unconditionally
whenever `params[:transitions]` is present.

**Suggested direction**

Have the writers return what they wrote rather than only what they refused —
they already build the row array, so the count is free — and let
`report_matrix_save` say *Successful update* only when that number is positive.
That also removes the duplicated arithmetic in the controller, which is the part
most likely to drift from the writers again.

**Resolution:** confirmed, then
fixed in all three places rather than one. The writers return a
`MatrixSaveResult` — `written` and `skipped`, summed across the projects of a
selection — instead of `skipped` alone, and the duplicated
`(projects × trackers × roles) − skipped` arithmetic is gone from the controller.
`report_matrix_save` says *Successful update* only when something was written;
when nothing was written and nothing refused it says so, with a new key
`notice_project_workflow_save_nothing_applied` (added and translated in all eight
locale files). The third place is `ProjectWorkflowsController`, which set the
notice whenever the request carried a matrix at all: it now reports the refusal
with `notice_project_workflow_not_own` when the writer lost the race against a
concurrent return to the generic workflow — which had been reported as a
successful save. **Red on the old code:** six examples — three in
`spec/controllers/workflows_controller_spec.rb` (whole payload rejected, on both
matrices, and every cell left at *(No change)*) and three in
`spec/controllers/project_workflows_controller_spec.rb` — all failing with
`expected: nil got: "Successful update."`. The *(No change)* case is a deliberate
departure from core, which reports success there: the new message covers both
causes in one sentence, because pressing Save and getting no feedback at all is
worse than either. Logged in `docs/DECISIONS.md`.

### F07 — `duplicate` skips the project-selection check that `copy` performs

- **Status:** fixed
- **Severity:** nit
- **Confidence:** confirmed
- **Category:** code-quality
- **Where:** `lib/redmine_project_workflows/patches/workflows_controller_patch.rb:123`
  (`copy`) and `:131` (`duplicate`)
- **Invariant touched:** none

**What is wrong**

`copy` runs `load_project_options` and then `return if invalid_project_selection?`.
`duplicate` runs `load_project_options` and never looks at what it collected;
`@invalid_project_ids` is filled and dropped. The two actions are the GET and
the POST of one screen.

**Why it matters**

Practically nothing: the copy form's controls are `source_project_id` and
`target_project_ids[]`, both validated separately and thoroughly (`unresolved_source?`
checks the *shape* as well as the record, precisely because core resolves with
`to_i`), and `params[:project_id]` is not read on that path. So a
`project_id=999999` on `duplicate` is ignored where the same value on `copy` is
a 404. The cost is a reader having to work out that the omission is harmless,
and `load_project_options` being called on a path that uses only its `@projects`
side effect without saying so.

**How I verified it**

Read-only, not executed. Read both actions and every consumer of
`@invalid_project_ids`.

**Suggested direction**

Either add the check for symmetry, or say in one line why `duplicate` does not
need it and that `load_project_options` is there for `@projects` alone.

**Resolution:** confirmed, and closed
with the finding's second option: `duplicate` now says in a comment why it does
not need the check and that `load_project_options` is there for `@projects`
alone. Adding the check was rejected — the action never reads
`params[:project_id]`, so a value there names nothing and can widen nothing, and
answering 404 for a parameter the action ignores reports a fault that does not
exist. Pinned by an example that is **green on the old code** and said to be:
*"ignores a project_id on the copy POST, which does not read it"* characterises
the deliberate asymmetry, so that adding the check for symmetry later fails an
example that explains itself. Nothing here was a defect to reproduce.

## What I checked and found sound

Recorded because an unstated pass reads as an unexamined one, and because a
later reviewer should not have to redo it.

- **INV-1 through INV-9.** Every path traced. No query on `workflows` executes
  without a `project_id` predicate — the five `grep` hits that look like
  exceptions (`ProjectWorkflowsController#transitions`, `StatusListQuery#base_scope`,
  `PermissionQuery` twice, `TransitionQuery`) are either multi-line calls that name it
  on the next line or base relations that every caller narrows before executing.
- **The three actions of INV-3 stay three.** `enable` / `return_to_inheritance` /
  `clear_rules` are the only writers of the scope table besides `ScopeCopier`,
  and none of them removes a scope implicitly. `ensure_scopes` is gone, as
  `docs/STATE.md` claims.
- **Both writers' delete predicates.** `pair_predicate`, `status_pair_predicate`,
  `each_batch_predicate` and `delete_permissions_for_scope` all `reduce` an
  array of conditions, which returns `nil` for an empty array and would make
  `where(nil)` match everything. Each of the four is guarded by an explicit
  empty check at every call site. This is the single most dangerous shape in the
  plugin and it is handled.
- **The R01 fix.** `rows_for_cell` reproduces core's row-by-row semantics
  exactly, including the case core gets right by accident — a flag left at *no
  change* is read back from `existing_flag_rows` rather than defaulted to false.
- **SQL construction.** Every value in the four raw statements
  (`copy_one_for_project`, `copy_generic_to_project`, `copy_scopes_sql`, the
  migration-004 backfill) is either `Integer()`-cast, `connection.quote`-d, an
  id read off an ActiveRecord object, or a constant checked against a
  server-built list first.
- **Authorization.** `spec/plugin_conventions_spec.rb`'s structural example —
  every action of `ProjectWorkflowsController` must be named by a permission —
  is the right shape for this, and it passes by inspection on the current action
  list. `find_rule_type` renders and every subsequent callback opens with
  `return if performed?`.
- **Migration reversibility, by reading.** 005's `down` re-adds the two indexes
  before 001's `down` removes them, and 003's `down` drops the foreign key
  before 002's `down` drops the index it needs. The order is right. (Not
  executed — see *Scope NOT covered*.)
- **The version-conditional helpers.** `project_workflows_summary_count_body`
  and `…_class` reproduce exactly the difference between 5.1's
  `icon-only icon-not-ok` span and 6.0+'s `decoration-red` class, which I
  confirmed by diffing `workflows/index.html.erb` between 5.1 and 7.0.
- **The bulk JavaScript.** Reads as carefully as the Ruby. `textContent` rather
  than `innerHTML`, `%{…}` replacement with numbers only so no `$&` hazard,
  a guard for a missing undo region, and the undo stack restores the value each
  control held *before* the action rather than at page load — which is the
  distinction the README bothers to explain and the code actually implements.
