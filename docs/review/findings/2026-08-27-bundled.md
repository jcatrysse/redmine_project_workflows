## Summary

Three independent reviews of this commit produced 24 distinct claims once
duplicates were removed. Re-verifying each of them against the code changed the
picture substantially: **thirteen of the 24 turned out to be factually wrong, to
describe a trade-off this repository has already recorded and decided, or to ask
for something that is already implemented.** That is not a criticism of the
reviewers — it is what happens when a repository writes its reasoning down as

the whole Redmine application refuse to boot on a version this plugin has not
been tested against.

What survived is one real correctness defect and a set of small, mostly local
improvements. The defect is that **the workflow copy screen takes no lock at all
on `project_workflow_scopes`** — it reads that table unlocked and then acts on
the answer, which is precisely the check-then-act shape `MatrixScope#writable_pairs`
was given `lock: true` to remove in 0.1.2, reintroduced on the one write path
nobody re-checked. One external review found it and described it as a lock
*ordering* problem whose worst outcome is a deadlock; that is one level too
shallow. There is an interleaving in which nothing collides, no error is raised,
and the copy commits reporting "Successful update" over project rules that sit
under no scope — the state ADR-001 exists to make unreachable, invisible to the
resolver, on PostgreSQL, with a green suite. The deadlock is the benign face of
this bug.

The most valuable thing that came out of the bundle is not a defect at all but a
measurement. This plugin copies **eleven** core method bodies. Hashing them

between 4.2 and 7.0, **both times semantically** — once turning

not hypothetical; it has already happened twice, in the method that decides

no network and no CI change, because in CI Redmine's own source is already on
disk.

Positively: no exploitable injection, XSS, CSRF or authorization bypass was

### F01 — The workflow copy screen takes no lock on the scope table

- **Status:** fixed
- **Severity:** major
- **Confidence:** confirmed
- **Category:** concurrency
- **Where:** `lib/redmine_project_workflows/patches/workflows_controller_patch.rb:166-181`,
  `lib/redmine_project_workflows/services/scope_writer.rb:95-105`,
  `lib/redmine_project_workflows/services/scope_combinations.rb:89-92`
- **Invariant touched:** INV-3
- **Source:** C (as a lock-ordering finding), escalated here

**What is wrong**

`WorkflowsController#duplicate` opens one transaction, writes `workflows` for
every target project, and only then reaches `record_scopes_for_copy`. That call
reads `project_workflow_scopes` through `ScopeCombinations.with_rules_and_no_scope`
— a plain `pluck`, no `lock:` anywhere on this path — and then acts on what it
read, creating scopes for the combinations it believes have rules and no scope
and stamping the rest. `grep -n 'lock: true' lib/` returns only
`scope_writer.rb:189`, `scope_writer.rb:218` and `matrix_scope.rb:48`; the copy
path is absent from that list.

That is the same check-then-act shape as the defect
`docs/review/findings/2026-08-27-codex.md` filed as F02 and closed by giving
`existing_combinations` a `lock:` keyword. The lock was added to the three
matrix and scope paths and not to the copy, and the resolution line for that
finding generalised the fix to "every caller takes scope rows before workflow
rows", which was not true then and is not true now.

**Why it matters**

Two outcomes, and the quiet one is worse.

*The loud one.* For a (project P, tracker T, role R) that has both a scope and
workflow rows, the copy holds the `workflows` row locks and then waits for the
scope row, while a concurrent *return to the generic workflow* holds the scope
row and waits for the `workflows` rows. The database kills one of them. The
transaction boundary means no partial data, so this is an availability defect: a
500 on a retryable action. Note that the other side of this race is **not**
necessarily a second administrator — `ProjectWorkflowsController` grants
`inherit`, `clear` and both matrix saves to `manage_project_workflow`, which is
a project-member permission.

*The quiet one.* Take the same combination in the state `ScopeWriter.clear_rules`
leaves behind: a scope with no rules under it — an own **empty** workflow, which
ADR-001 names as a supported configuration. Then:

1. the copy's `delete_all` locks nothing, because there are no rows;
2. the copy inserts its rows; under READ COMMITTED the concurrent return cannot
   see them;
3. the return's `delete_rules` therefore deletes nothing and waits for nothing —
   **no cycle, no deadlock**;
4. the copy reads `with_rules_and_no_scope`; the scope row is still visible
   because the return has not committed, so the triple is excluded and no scope
   is created;
5. the copy's `touch_combinations` UPDATE blocks on the return's `FOR UPDATE`;
6. the return commits, deleting the scope row;
7. the copy's UPDATE matches zero rows — no error;
8. the copy commits and sets `notice_successful_update`.

The end state is project rules in `workflows` under no scope. The resolver
ignores them (INV-3), so they apply to nothing, nothing will ever clean them up,
and the request that wrote them reported success. `docs/design.md:105-120`
describes exactly this state as the defect the locking was introduced to remove.

**How I verified it**

Read the call chain, then reproduced it. Two live `psql` sessions against a
throwaway PostgreSQL 16.13 cluster, issuing the statement shapes the two code
paths issue, on a two-table fixture mirroring `workflows` and
`project_workflow_scopes`:

```
sessie A (copy)                  sessie B (return to generic)
BEGIN
DELETE 2   <- workflow locks     BEGIN
                                 SELECT ... FOR UPDATE  <- scope lock
                                 DELETE ...  (waits on A)
UPDATE project_workflow_scopes ...  (waits on B)
ERROR:  deadlock detected
DETAIL:  Process 6381 waits for ShareLock on transaction 740;
         blocked by process 6382.
         Process 6382 waits for ShareLock on transaction 739;
         blocked by process 6381.
CONTEXT: while updating tuple (0,1) in relation "project_workflow_scopes"
ROLLBACK                         COMMIT
```

I then re-ran the same interleaving with the copy taking the scope lock first,
and the two transactions serialised: both committed, no error, and the return's
delete found zero rows because the copy had already removed them. So the
diagnosis and the direction below are both measured rather than argued.

The quiet interleaving was established by reading, not reproduced — it needs the
two transactions driven from Rails to hit steps 4 and 5 in the right order, and
this container has no Redmine host. That is the one part of this finding a fixer
should re-establish before relying on it.

**Suggested direction**

Make the copy's read of the scope table and its write of `workflows` one
decision, the way `MatrixScope#writable_pairs` already does for a matrix save.
The target triples are computable before any write — they are the resolved
target projects times the target trackers and roles, minus the pairs whose
source resolves to the target itself, and none of that consults the tables. So a
lock over the existing scope rows of that set, taken by primary key in id order
(which is what `ScopeWriter.lock_combinations` already does, and what makes two
callers queue rather than deadlock), can be the first statement inside the
transaction.

Two things to decide rather than inherit. First, whether the copy should also
*use* the locked answer, as `writable_pairs` does — the copy legitimately creates
scopes where none exist, so it cannot simply filter its targets, and the fixer
should work out what the copy is entitled to do to a combination whose scope
disappeared while it ran. Second, the residual case: a combination with **no**
scope row is serialised by the unique index rather than by a lock anyone can
pre-take, so copy-versus-`ScopeWriter.enable` can still form a cycle after this
fix and no row lock can close it. That is worth recording rather than chasing;
if it is ever actually observed the answer is a `rescue ActiveRecord::Deadlocked`
on the copy action, not a wider lock.

For the test: a single-connection example asserting the statement order is
deterministic and cheap, and `spec/services/workflow_concurrency_spec.rb:60-72`
already has the `statements_during` / `index_of_scope_lock` /
`index_of_first_rule_write` helpers to write it with. A second two-connection
example would need `use_transactional_tests = false`, two real connections and a
timing window in all nine cells; `docs/STATE.md:481` already records how fragile
that shape is, so weigh it before adding one.

**Resolution:** `fixed`. `WorkflowsController#duplicate` now calls
`ScopeWriter.lock_scopes_for_copy` as the **first** statement in its
transaction, over the combinations the copy is about to write. Those come from
`WorkflowRule.copy_pairs_for_project`, extracted out of `copy_for_project` so
that the lock set and the write share one skip rule rather than two copies of
it — duplicating that rule is how a lock comes to cover a different set from the
write it protects. The lock names existing scope rows by primary key in
**ascending id order** and filters no rule type, so it queues against
`lock_combinations`' three callers rather than deadlocking with them, and covers
both rule types the copy replaces.

**The quiet interleaving was re-established before anything relied on it, and
reproduced rather than read.** Driven from Rails with two live connections
against 7.0-stable + PostgreSQL 16: a throwaway spec with
`use_transactional_tests = false`, a scope carrying no rules (the state
`clear_rules` leaves), the copy's own transaction body on the main thread and
`return_to_inheritance` on a second connection, interleaved by wrapping
`ScopeWriter.delete_scopes` so the returner holds its lock and pauses before
committing. Old code: `project rules=1  scope exists=false` — one rule in
`workflows` under no scope, no error, no deadlock. Same probe with the lock
taken: `project rules=0  scope exists=false` — the return queued behind the copy
and removed everything, which is a legitimate return-last-wins serialisation and
leaves nothing orphaned. The probe was deleted; it needs a fixed timing window,
which `docs/STATE.md` records as fragile across nine cells.

What ships instead is what the finding recommended: three deterministic
single-connection examples in `spec/controllers/workflows_controller_spec.rb`
(`the lock the copy screen takes`), driving the real `duplicate` action and
asserting statement order. **Two of the three are red on the old code** — run
against `3cdad5e`'s `lib/` with the new `spec/` in place, both failing on
`index_of_scope_lock(statements)` being nil. The third, a copy into the generic
workflow taking no lock, passes on both and is named here as the companion it is.
The second red one asserts the lock covers a scope with *no rules under it* —
the combination the copy's own delete cannot lock, and the one the quiet path
needs — by capturing what the `FOR UPDATE` statement returned, because the row
ids travel as bind parameters and are not in the SQL text.

Both questions the finding left open are answered rather than inherited. The copy
does **not** filter its targets by the locked answer: it is entitled to create a
scope where none exists, and with the lock held first every order now ends
consistently — if the return commits first the copy's read sees no scope, writes
its rules and `ensure_scopes_for_existing_rules` creates one; if the copy commits
first the return removes both. The residual case is recorded, not chased: a
combination with **no** scope row has nothing to pre-take, so copy-versus-`enable`
is serialised by the unique index and can still cycle. That is now written down in
`ScopeWriter.lock_scopes_for_copy` and in `docs/design.md`, with the answer if it
is ever observed (`rescue ActiveRecord::Deadlocked` on the action, not a wider
lock).

The four copy helpers moved to a new
`Patches::WorkflowsControllerCopy` — `Metrics/ModuleLength` crossed at 260/250,
and that limit is already relaxed with a rationale, so it was extracted rather
than raised, following the split `WorkflowsControllerProjectSelection` already
established. Every method there is private.

Gates: migrations up → 0 → up clean on both hosts **before** the suite (leftover
tables/columns `[]`, plugin rows in `schema_migrations` `[]`); suite **674
examples, 0 failures** on 5.1-stable and 7.0-stable + PostgreSQL 16; RuboCop 97
files, no offences; `zeitwerk:check` clean on both; `node dev/check-bulk-js.mjs`
28 checks pass.

### F02 — `docs/design.md` states a lock-order rule that one path does not obey

- **Status:** fixed
- **Severity:** minor
- **Confidence:** confirmed
- **Category:** docs
- **Where:** `docs/design.md:118-120`, and
  `docs/review/findings/2026-08-27-codex.md:165`
- **Invariant touched:** none
- **Source:** V

**What is wrong**

`docs/design.md:118-120` reads: *"Every path therefore takes scope rows before
workflow rows, which is also what keeps a save and a return to the generic
workflow from deadlocking rather than queueing."* The sentence is true of
`writable_pairs`, `return_to_inheritance` and `clear_rules`, and false of
`WorkflowsController#duplicate`. The `Resolution:` line of the codex finding that
introduced the locking says the same thing in the same words.

**Why it matters**

Under `CLAUDE.md`'s rule that code and documentation disagreeing makes one of
them a finding, this is a finding in its own right — but the reason it matters is
sharper than a reader being misled later. That sentence is what made the 0.1.2
fix look complete. A universal claim was written down on the strength of three
paths having been changed, and the fourth was never checked against it.

**How I verified it**

Read both documents against the four write paths; `grep -rn 'scope rows before'
docs/` and `grep -n 'lock: true' lib/` are the whole of it.

**Suggested direction**

If F01 is fixed, the sentence becomes true and needs only the residual case
noted beside it. If F01 is deferred, the sentence has to name the three paths
that do obey the rule and say that the copy path does not, because leaving a
universal claim standing over a known exception is how the next session skips
the check.

**Resolution:** `fixed`, and fixed the way the finding asked rather than by
correcting a number. F01 landed, so the claim could simply have become "every
path" again with the count changed to four. Instead `docs/design.md` now names
the fourth path and *why it was missed* — a universal claim recorded from a
sample of three — and states the scope-order rule with the qualification it
actually has: it holds on all four paths **for combinations that have a scope
row**, and a combination with none is serialised by the unique index instead,
where copy-versus-`enable` can still cycle. Naming the exception in the same
paragraph is what stops the next session generalising from the paths it happened
to change.

No test: this is a documentation claim, and there is nothing in it a spec can
assert that F01's three examples do not already assert about the code. Said
plainly rather than dressed up as covered.

### F03 — Nothing would notice a copied core method changing under the plugin

- **Status:** fixed
- **Severity:** major
- **Confidence:** confirmed
- **Category:** spec-conformance
- **Where:** `lib/redmine_project_workflows/patches/issue_patch.rb`,
  `project_patch.rb`, `workflows_helper_patch.rb`,
  `workflows_controller_patch.rb`, `role_patch.rb`, `tracker_patch.rb`
- **Invariant touched:** none directly; INV-4 is why the copies exist
- **Source:** B

**What is wrong**

Eleven core method bodies are copied into this plugin with one or two
project-blind queries replaced. `grep -n 'super' lib/redmine_project_workflows/patches/`
returns six code hits, all in the four controller actions and two helpers that
delegate for non-project requests; the other eleven are full reimplementations
with no `super` to fall through to. `docs/design.md`'s integration-points table
lists the core code the plugin touches but never says which entries are copies
and which delegate, and `Role#copy_workflow_rules` and
`Tracker#copy_workflow_rules` are absent from it.

The plugin declares `requires_redmine version_or_higher: '5.1'`, so 5.2, 6.0,
6.2, 7.1 and every future release install without objection, and nothing
compares the copies against what core actually holds on the host they are
running on.

**Why it matters**

This is measured, not hypothetical. Extracting each copied body from
`4.2-stable`, `5.0-stable`, `5.1-stable`, `6.1-stable` and `7.0-stable` and
hashing it with comments and whitespace normalised:

| copied method | 4.2 | 5.0 | 5.1 | 6.1 | 7.0 |
| --- | --- | --- | --- | --- | --- |
| `Issue#tracker=` | = | = | = | = | = |
| `Issue#new_statuses_allowed_to` | a | a | **b** | b | b |
| `Issue#workflow_rule_by_attribute` | a | a | **b** | b | b |
| `Project#rolled_up_statuses` | a | a | **b** | b | b |
| `WorkflowsHelper` × 3 | = | = | = | = | = |
| `WorkflowsController#permissions` / `#update` / `#update_permissions` | — | a | a | **b** | b |

Both changes to `Issue#new_statuses_allowed_to` in that window were semantic:

```
4.1 -> 4.2   if blocked? || descendants.open.any?     ->  unless closable?
             if ancestors.open(false).any?            ->  unless reopenable?

5.0 -> 5.1   user.admin ? Role.all.to_a
               : user.roles_for_project(project)      ->  roles_for_workflow(user)
```

The second adds a `consider_workflow?` filter to the role list. A plugin
carrying the 5.0 copy onto 5.1 would have offered status transitions for roles
that take no part in a workflow — a permission widening, silent, with the
plugin's own specs green, because those specs assert the plugin's expected
answers rather than core's. The drift within the currently supported window
(5.1 → 7.0) is cosmetic by comparison (`sub` → `delete_suffix`,
`each` → `each_value`), which is a fact about this window and not a property of
the mechanism.

The two methods most exposed are also the two that decide authorization:
`Issue#new_statuses_allowed_to`, which `Issue#safe_attributes=` calls on every
issue save, and `Issue#workflow_rule_by_attribute`, which decides which fields
are read-only or required.

**How I verified it**

`curl` of each core file from the five branches, then the method bodies
extracted by matching `def <name>` to the dedented `end` and hashed after
stripping comments and collapsing whitespace. The two diffs above are `diff` of
the extracted bodies. I also prototyped the detection mechanism described below
in plain Ruby 3.3.6 and confirmed it works for all three prepend shapes this
plugin uses — a class (`Issue`), a module (`WorkflowsHelper`) and a singleton
class (`WorkflowTransition.singleton_class`).

**Suggested direction**

Detection, not declaration. **Do not narrow `requires_redmine` to a range**: core
supports one (`lib/redmine/plugin.rb:252-258`), but `:254` raises
`PluginRequirementError` and `lib/redmine/plugin_loader.rb:61` has no rescue
around `run_initializer`, so on an out-of-range Redmine the whole application
refuses to boot until an administrator deletes the plugin directory. That trades
an uncertain divergence for a certain outage.

What is available instead costs nothing at runtime: the suite runs *inside* the
host Redmine checkout, so core's source is already on disk in every one of the
nine cells. `UnboundMethod#super_method` reaches core's own definition through
the prepend, and `RubyVM::AbstractSyntaxTree.of` gives its line range, so a spec
can read the eleven bodies off the host, normalise and digest them, and compare
against a checked-in table keyed by Redmine minor. No gem, no network, no CI
change. On the churn rate above it fires roughly once per Redmine minor, which
is exactly the moment somebody should be looking.

Worth pairing with it, because it catches a class the digest cannot: `super_method`
also **binds**, including for private methods, so an example can call core's own
implementation as an oracle and assert that plugin and core agree wherever no
scope applies. Scope such examples to a state with no project rows, since core's
query has no `project_id` predicate and a fixture leak would turn them into
false failures on all nine cells.

Two smaller pieces belong with this: `docs/design.md`'s integration-points table
should say which entries are copies and which delegate, and add the two
`copy_workflow_rules` replacements; and `init.rb:14`'s comment should record that
the 5.1 floor is a **hard dependency** — `roles_for_workflow` does not exist
before 5.1 — rather than merely the oldest version anyone has tested, so a later
session does not lower it back to 5.0 on the grounds that the floor is only a
testing claim.

**Resolution:** `fixed`, detection rather than declaration, and
`requires_redmine` was **not** narrowed — the reason is recorded in
`docs/design.md` and in `init.rb` so it is not re-proposed.

**The gate.** `spec/upstream/core_drift_spec.rb` plus
`spec/upstream/core_method_digests.yml`, over a new
`Services::CoreMethodDigest`. It reads core's own body for every method the
plugin shadows off the host under test, via `UnboundMethod#super_method` and
`RubyVM::AbstractSyntaxTree.of`, normalises comments and whitespace away, digests
it, and compares against the checked-in table keyed by Redmine minor. No gem, no
network, no CI change.

**Eighteen methods, not eleven, and the set is discovered rather than listed.**
That difference matters twice over. It includes the delegates — a delegate can
drift too, because what it delegates *to* is still core's — and it includes the
two that are **private in core**, one of which is
`Issue#workflow_rule_by_attribute`, the method that decides which fields are
read-only or required. A first draft used `instance_methods(false)` alone and
silently covered thirteen of fifteen; the service now takes private methods too
and says why. A hand-kept list of eleven would have lost this property on its
first edit.

**Measured, and the measurement refines the finding's table.** Within the
supported window 6.1 and 7.0 are **identical** on all eighteen, and 5.1 differs
in exactly three — `WorkflowsController#update`, `#permissions` and
`#update_permissions`. That is what F03's five-branch table predicted, now
confirmed from three real checkouts (the 6.1 host was built for this rather than
left as a gap, so the table covers all three minors and no CI cell meets an
unmeasured host).

**The oracle half is the reason a digest bump is not just paperwork.**
`super_method` binds, so core's implementation is callable: four examples assert
the plugin agrees with core wherever no project has taken a workflow over, one
asserts it **stops** agreeing once one has — an oracle suite that only asserted
agreement would pass over a plugin that had quietly become core again — and the
whole group is scoped to a state with no project rows, as the finding warned.

**Proved by firing, three times, and two of those probes found real defects in my
own work:**

1. *Digest drift.* One expected digest set to a wrong value: the group failed
   naming the method, both digests, and core's exact `source_location` with line
   number. It also exposed a genuine bug — YAML parsed the all-zero digest as an
   **Integer**. The table's values are now quoted, with the reason in its header.
2. *Semantic drift, first attempt.* `TransitionQuery` was reverted to core's
   pre-5.1 role list (`user.admin ? Role.all : user.roles_for_project`), which is
   the exact historical widening F03 measured. **The oracle passed.** Two causes,
   both mine: no role in the fixture had `consider_workflow?` false, so the two
   role lists agreed; and worse, the examples ran against `Issue.new`, which
   resolves from core's `old_status_id = 0` pseudo-status, so no transition
   matched and **the examples were comparing two empty arrays**. A gate that
   passes vacuously is worse than no gate, and only a probe finds that.
3. *Semantic drift, after the fix.* The oracle now uses a saved issue with a
   current status and a role holding `view_issues` only (`consider_workflow?` is
   `add_issues || edit_issues`). The same reversion now fails: plugin `[1, 2, 4]`
   against core `[1, 2]` — status 4 offered through a role that takes no part in
   a workflow, which is the silent permission widening, caught. Both probes were
   reverted; `git status` clean.

**The two smaller pieces.** `docs/design.md`'s integration-points table gains a
**`How`** column — copy / delegates / left alone — on all 21 rows, with a
paragraph defining each and describing the gate. (One correction to the finding:
`Role#copy_workflow_rules` and `Tracker#copy_workflow_rules` were **not** absent
from that table; they were already a row, now marked **copy**.) And `init.rb`'s
comment now says the 5.1 floor is a **hard dependency** — `roles_for_workflow`
does not exist before 5.1 and `TransitionQuery` calls it, verified in the 5.1
checkout at `app/models/issue.rb:2110` — so lowering it ships a `NoMethodError`
on every issue save rather than widening support.

Gates: suite **693 examples, 0 failures** on **all three** Redmine minors
(5.1-stable, 6.1-stable, 7.0-stable) + PostgreSQL 16 — three of the nine cells
rather than the usual two, because the 6.1 host was built for the digest table;

### F04 — The transition query pays a join and a subquery where core pays one join

- **Status:** fixed
- **Severity:** minor
- **Confidence:** confirmed
- **Category:** performance
- **Where:** `lib/redmine_project_workflows/services/transition_query.rb:44-49`
- **Invariant touched:** none — INV-4's predicates all live in `combined_scope`

**What is wrong**

  .where(WorkflowTransition.table_name => { id: combined_scope.select(:id) })
  .distinct
  .to_a
  .sort
```

A join plus a subquery against the same table. Core's

identically on 5.1-stable and 7.0-stable.

**Why it matters**

This is the hottest path the plugin owns. `Issue#safe_attributes=` calls
`new_statuses_allowed_to` unconditionally on every issue save, and the bulk-edit
form, the bulk-save loop and the context menu each fan it out once per selected

extra work per call is one primary-key lookup back into `workflows` per matching

that it is three concepts where one suffices, in the file a maintainer opens
first when comparing the plugin against core.

**How I verified it**

Read both implementations; core's fetched from `5.1-stable` and `7.0-stable` and
compared. The call sites were established by grepping core for
`new_statuses_allowed_to`.

**Suggested direction**

One statement, no join, no `DISTINCT`:

IssueStatus.where(id: combined_scope.select(:new_status_id)).to_a.sort

untouched so every `project_id` predicate stays where it is, and a NULL

**Resolution:** `fixed`, and with the version the finding said to take rather

### F09 — `CURRENT_TIMESTAMP` is not UTC on MySQL or MariaDB

- **Status:** fixed
- **Severity:** minor
- **Confidence:** confirmed
- **Category:** portability
- **Where:** `lib/redmine_project_workflows/services/scope_copier.rb:86`,
  `db/migrate/004_create_project_workflow_scopes.rb:60-73`
- **Invariant touched:** none
- **Source:** A, filed there as unverified; settled here

**What is wrong**

Both places write `CURRENT_TIMESTAMP` into `created_at` and `updated_at`, and
migration 004's comment justifies it: *"Rails puts every supported adapter's
session in UTC, so all three agree on the value."* That is true for PostgreSQL
and false for MySQL and MariaDB.

- PostgreSQL: `postgresql_adapter.rb` sets the session timezone to UTC when
  `default_timezone == :utc` — `variables["timezone"] = "UTC"` in Rails 6.1,
  `raw_execute("SET SESSION timezone TO 'UTC'")` in 8.0.
- MySQL: `abstract_mysql_adapter.rb#configure_connection` sets `sql_auto_is_null`,
  `wait_timeout` and `sql_mode` and **no** `time_zone`, in 6.1, 7.2 and 8.0.
  `mysql2_adapter.rb:160` sets `query_options[:database_timezone]`, which decides
  how returned values are *tagged*, not what the server computes.

So on MySQL and MariaDB `CURRENT_TIMESTAMP` returns the server's local time and
Rails reads it back as if it were UTC.

**Why it matters**

On a MySQL or MariaDB host whose server timezone is not UTC — six of the nine
supported cells — the audit columns of every scope written by these two paths are
off by the server's offset, and the inventory and settings tab then render
"Updated … ago" wrong by that much, possibly in the future. Nothing about the
resolver, a rule or an authorization decision depends on these columns, and the
blast radius is smaller than it first looks: `project_workflows_helper.rb:214`
returns early when `updated_by` is blank, so migration 004's backfilled scopes
never display a time at all and only `ScopeCopier`'s author-stamped rows can show
a wrong one.

The larger cost is the false claim. It stands in a migration comment and in
`docs/DECISIONS.md`, so the next author reaches for `CURRENT_TIMESTAMP` believing
it is UTC everywhere.

**How I verified it**

Read `configure_connection` in `abstract_mysql_adapter.rb` and
`postgresql_adapter.rb` from Rails `v6.1.7`, `v7.2.2` and `v8.0.2`, and grepped
both MySQL adapters for `time_zone` — no hit in 6.1 at all, and only
`database_timezone` in the later two.

I also tested the *reason* the comment gives, which is the other half wrong. On a
throwaway PostgreSQL 16.13 cluster with the session timezone set to UTC, a bare
quoted timestamp literal in the `SELECT` list of an `INSERT ... SELECT` is
coerced to the target `timestamp` column without any cast:

```
INSERT INTO dst (project_id, created_at, updated_at)
  SELECT project_id, '2026-08-27 09:15:00', '2026-08-27 09:15:00' FROM src ...
-- INSERT 0 1, stored as 2026-08-27 09:15:00
```

**Suggested direction**

Build the timestamp in Ruby and let `default_timezone` apply, rather than asking
three databases to agree about `CURRENT_TIMESTAMP`. `connection.quoted_date` is
the existing tool for it. The standard type-keyword form, `TIMESTAMP '...'`, is
accepted by all three and is more explicit than a bare literal, so it is the
safer shape even though the bare one measured fine on PostgreSQL. Then correct
the comment in migration 004 and supersede the claim in `docs/DECISIONS.md`.

Touching a shipped migration is a judgement call the fixer owns: leaving 004
alone and fixing only `ScopeCopier` closes the live path, since the backfill's
rows display no time anyway. Say which was chosen and why.

**Resolution:** `fixed` in **both** places, and here is the judgement call the
finding left to the fixer, made and reasoned rather than deferred.

**I changed migration 004 as well as `ScopeCopier`.** The argument for leaving it
alone is real — a shipped migration does not re-run, so the change reaches only
installations that migrate from here on, and a backfilled scope displays no time
at all anyway because `project_workflows_helper.rb` returns early when
`updated_by` is blank. But that argument stops at "the wrong value is currently
invisible", not at "the value is right". Leaving a statement we have already
diagnosed as wrong means every future installation inherits it, and the
divergence between old and new installations is harmless for exactly the reason
that made leaving it tempting. Fixing only the live path would have closed it
while knowingly shipping the defect.

Both now build the value in Ruby: `connection.quoted_date(Time.now.utc)` wrapped
in the standard `TIMESTAMP '...'` type keyword, which all three adapters accept
and which says what it means.

**Three documents carried the false claim and all three are corrected**, because
the finding is right that the claim was the larger cost. Migration 004's comment
now says which half was wrong and why (both halves were: `CURRENT_TIMESTAMP` is
not UTC on MySQL/MariaDB, *and* PostgreSQL 16.13 does coerce a bare quoted
literal in a `SELECT` list — measured). `docs/DECISIONS.md`'s 2026-08-26 entry is
marked **SUPERSEDED** with the original text kept, rather than edited in place,
per this repository's append-only rule. `docs/STATE.md`'s trap entry is replaced
by the correction.

### F10 — The inventory's default mode is linear in the number of decisions taken

- **Status:** fixed
- **Severity:** minor
- **Confidence:** confirmed
- **Category:** performance
- **Where:** `lib/redmine_project_workflows/services/inventory_query.rb:16-21`
  and `:97-110`
- **Invariant touched:** none
- **Source:** B

**What is wrong**

The class comment says a page costs the same on an installation with three
projects and one with three thousand. That is true of the "everything" mode,
where `product_slice` addresses the product arithmetically. It is not true of
`deviations_only`, which is the **default**: `deviating_triples` plucks every
matching scope triple, materialises it, sorts it in Ruby and only then slices
`[offset, limit]` — and `#total` pays the same price.

**Why it matters**

Measured on this container (Ruby 3.3.6), the Ruby half alone:

| distinct triples | `sort_by` | retained |
| --- | --- | --- |
| 10,000 | 24 ms | ~1 MB |
| 100,000 | 251 ms | ~9 MB |
| 1,000,000 | 2.8 s | ~92 MB |

Repeated on every page change, since the memo is per-instance and per-request by
design. At the sizes this plugin's own model produces it is a non-event: a scope
row exists per *decision actually taken*, and a million of them would mean
essentially every project overriding essentially everything, which contradicts
the premise that the generic workflow keeps working for projects that do not
override it. So the finding is real and scaled at the top end of implausible —
and the comment promising constant cost is what makes the next reader optimise
the wrong branch or file this again.

The project settings tab is not affected: it passes `deviations_only: false` for
a single project and takes the bounded branch.

**How I verified it**

Read the two modes. Benchmarked the sort in isolation — 10k, 100k and 1M
three-element arrays with three hash lookups per key, timed and measured for
allocations — rather than inferring it.

**Suggested direction**

The comment first: name the mode each cost belongs to, with the numbers.
`docs/design.md`'s inventory paragraph is the place for the measured figures, in
the same voice as "What an administration save costs".

If the constant is worth reducing, it is available inside the existing method
without touching SQL — a single packed integer sort key in place of the
three-element array is order-preserving by construction here, because each index
is strictly bounded by its list's size. **Do not** move the ordering into SQL, as
the source review proposed: the order comes from `lft`, `position` and
`builtin, position`, all integer columns, so the determinism argument is not what
is at stake, and the cost is a permanent three-table join plus a duplicated copy
of three core ordering scopes plus a pagination path to re-prove on nine cells.
Against maintainability first, that is a losing trade.

applied, `inventory_query.rb:104` renders every project id into the SQL text, so

Migration 004's cascading foreign keys mean that predicate cannot change the
result set when the list is literally every project, so passing no predicate
there would be behaviour-preserving — and INV-4 governs `workflows`, not this
table.

**Resolution:** `fixed` as a documentation fix with a property test, which is
what the finding asked for — the comment first, and **not** the SQL rewrite.

bounded by configuration variety instead of project count, on both the
administration screen and the issue list. INV-4 allows a list verbatim, no tree
walk is introduced, and it is ordinary ActiveRecord on all three adapters.

1. *Two projects each overriding only one role, generic rows for both* — the

### F18 — Two undocumented traps around core's callback chain and INV-4

- **Status:** fixed
- **Severity:** nit
- **Confidence:** confirmed
- **Category:** docs
- **Where:** `docs/STATE.md` (traps list), `CLAUDE.md` INV-4,
  `lib/redmine_project_workflows/patches/workflow_rule_patch.rb:195-216`
- **Invariant touched:** INV-4, in its wording
- **Source:** A and V

**What is wrong**

Two separate things, both documentation, both about a future session doing the
obvious thing and being wrong.

*The callback trap.* ActiveSupport's callback dedupe compares only kind and
filter — `Callback#duplicates?` → `matches?(kind, filter)` — and `only:` is
stored as a separate `:if` condition, not in the filter. So
`prepend_before_action :require_admin, only: [...]` on `WorkflowsController`
would **delete core's unconditional registration** and leave `index`, `copy` and
`duplicate` ungated. Verified in the Rails source for 6.1, 7.2 and main. This is
not a defect in the current code — nothing prepends anything there — and it is
precisely the "improvement" a session working on F05 would reach for.

*The INV-4 exception.* `WorkflowRule.copy_one_with_projects:205` issues
`where(tracker_id:, role_id:).delete_all` with no `project_id` predicate, and the
`INSERT ... SELECT` two lines below carries `project_id` through the select list,
so both statements deliberately span the generic and project populations. The
method comment at `:195-200` explains why the reach is deliberate but never
mentions INV-4, and INV-4 in `CLAUDE.md` says "**any** query against `workflows`
carries an explicit `project_id` predicate" with no exception listed.

**Why it matters**

The first is a latent authorization bypass with a plausible route to being
introduced. The second is an invariant whose letter is broken in one place, in
the file a reviewer greps first, with no record either way — so it will be
re-found every review, and the plausible "repair" is worse than the state: fixing
only the DELETE leaves the INSERT non-compliant two lines below and risks
half-copying a duplicated role.

**How I verified it**

For the callback dedupe: read `prepend_one`, `remove_duplicates`, `duplicates?`
and `matches?` in `activesupport/lib/active_support/callbacks.rb` at `v6.1.7`,
`v7.2.2` and `main`, and confirmed `ApplicationController` registers `user_setup`
at `:64`, before `WorkflowsController`'s own callbacks. For INV-4: read the
method and grepped every `workflows` query in `app/` and `lib/` — this is the
only one without a project predicate.

**Suggested direction**

Add the callback behaviour to `docs/STATE.md`'s traps list, where the entries
that cost time once already live. For INV-4, change the documentation rather than
the code: name `copy_one_with_projects` as the single deliberate exception, in
`CLAUDE.md` or in `docs/design.md` beside the `Role#copy_workflow_rules` row, and
say that both its statements span the two populations because "duplicate this
role including every project's workflow" is defined that way. If the letter must
hold in code instead, the precedent is in the same file —
`delete_duplicate_rules!:250-251` sweeps the two populations separately — but
that is two statements where the comment at `:191-194` says one was chosen to
avoid 500 round trips per tracker, so it is a trade rather than a cleanup.

While in this area, one more undocumented divergence worth a clause:
`Project#rolled_up_statuses` is memoised in `project_patch.rb:19` where core is
not, and `rolled_up_project_tracker_ids` is a new **public** method on `Project`.
The memo is defensible — core reserves and clears that same ivar in
`Project#reload` on all three versions — but the comment claims the body is
core's and mentions neither.

**Resolution:** `fixed`, both halves, and one of them turned out to have a
testable part.

*The callback trap* is now an entry in `docs/STATE.md`'s traps list, with the
mechanism (`Callback#duplicates?` → `matches?(kind, filter)`, `only:` stored as a
separate `:if`), the consequence (`index`, `copy` and `duplicate` left ungated),
the three Rails versions it was read in, and — the part that makes it useful —
the safe alternative, which is the guard clause F05 just landed. It is also
restated in the comment on `find_trackers_roles_and_statuses_for_edit`, because
that is where somebody stands when they reach for the wrong fix.

*The INV-4 exception* is named in `CLAUDE.md`, in INV-4 itself rather than in a
footnote: `WorkflowRule.copy_one_with_projects` is the single deliberate
exception, both of its statements span the two populations because "duplicate
this role including every project's workflow" is defined that way, and the
plausible repair — scoping the `DELETE` alone — is spelled out as worse than the
state, because the `INSERT … SELECT` two lines below spans them too. The method's
own comment says the same and adds why F01's lock is *not* extended there (core
calls it only on a record it has just created, so there is nothing to contend
for — the thirteenth "checked and not filed" row, now written where a reader of
that method will find it).

The testable part: `spec/plugin_conventions_spec.rb` now asserts the exception is
**exactly one**, following the `insert_all` grep-gate already in that file — one
marked method, `WorkflowRule` still answering to it, and `CLAUDE.md` still naming
it. A grep for the exception rather than for compliance, and the example says why:
asserting no *other* query lacks a predicate would need to follow relations built
across the query services, and a regex that tried would fail on the ones naming
`project_id` two calls away. What it buys is that the exception cannot quietly
become two.

Honest about the red-on-old-code claim: that example fails on the old tree
because the marker comment did not exist there, which is evidence about the
documentation and not about behaviour. Said rather than counted.

Also folded in, from the finding's closing clause: `project_patch.rb`'s comment
claimed the body was core's and mentioned neither that `rolled_up_statuses` is
memoised where core's is not, nor that `rolled_up_project_tracker_ids` is a new

request actually did.

Read the four reporting methods; grepped `app/` and `lib/` for `Rails.logger` —

One `Rails.logger.info` per outcome branch in the four methods that already hold

operator by name.

**What is wrong**

1. `README.md`'s Installation section is three numbered steps and a warning about
   `RAILS_ENV`. It says nothing about what the migrations do to Redmine's central

2. Migration 003 deletes workflow rows whose `project_id` names no existing

3. `docs/design.md:257-271` discusses an InnoDB constraint on this table — error

**Why it matters**

Item 3 is a real adapter fact affecting six of the nine cells and recorded

column and all three run in one rake invocation. So the one statement that is not
metadata-cheap always sees the generic matrix alone.

**How I verified it**

Measured. A synthetic `workflows` table of 900,000 rows / 80 MB heap — 25
trackers × 20 roles × 30 statuses, dense in both transitions and permissions,
ten to fifty times larger than realistic — on PostgreSQL 16.13 with default
`maintenance_work_mem`, running the plugin's actual DDL:

```
ALTER TABLE workflows ADD COLUMN project_id integer          1.3 ms
CREATE INDEX  (four of them)                          1.6 s - 2.3 s each
DELETE FROM workflows WHERE project_id NOT IN (...)  129 ms, DELETE 0
ALTER TABLE ... ADD CONSTRAINT FOREIGN KEY             77 ms
DROP INDEX (two of them)                          1.6 ms / 1.1 ms
migration 004 backfill INSERT..SELECT over 450k rows  204 ms
                                                    ------------
total DDL                                              ~7.4 s

Four or five sentences in `README.md` under Installation saying what the
migrations touch, roughly how large that table is and why, and that the one
rebuild is 003's foreign key on MySQL and MariaDB. `say_with_time` plus
`connection.delete` in 003 so the block returns an Integer and the row tally
prints. One clause in `docs/design.md:257-271` about the COPY algorithm.

**Do not** adopt the rest of what the source review asked for — `CREATE INDEX

**3. `docs/design.md`**'s InnoDB section now states that 003's `add_foreign_key`
