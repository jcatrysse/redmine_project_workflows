## Summary

The plugin has unusually explicit domain invariants and generally enforces them through narrow query and writer services. Project scoping is consistently visible in workflow queries, write paths are transactional, project-level actions authorize against the project from the route, and the test suite is broad and organised around past regressions. The most concerning remaining area is the administration copy action: inherited loose validation from Redmine core becomes more consequential after the plugin adds project sources and multiple project targets. A malformed or stale source tracker/role id is treated as the intentional “any” selection, and target tracker/role ids are only partially resolved, so an administrator can silently copy a broader or narrower workflow than requested. No blocker was found by static review, but runtime confidence remains limited until the supported host suites and migration round trips are rerun.

### F01 — An invalid source tracker or role silently becomes “any” during workflow copy

- **Status:** fixed
- **Severity:** major
- **Confidence:** confirmed
- **Category:** correctness
- **Where:** `lib/redmine_project_workflows/patches/workflows_controller_patch.rb:132-169`; upstream Redmine 5.1/6.1/7.0 `WorkflowsController#find_sources_and_targets`
- **Invariant touched:** none

**What is wrong**

`find_sources_and_targets` converts a non-existent source tracker or role id to `nil`. Both Redmine core and the plugin then reject the source only when *both* resolved objects are nil. But `nil` also represents the deliberate `any` selection. Thus a request containing a real role and a non-existent tracker passes validation and is handed to `WorkflowRule.copy_for_project` as “any tracker for this role”; the symmetric case broadens to any role for a tracker. The plugin validates `source_project_id` strictly, but does not apply the same existence/shape distinction to the tracker and role that identify the source workflow.

**Why it matters**

An administrator submits a stale form, hand-built request, or URL with `source_tracker_id=999999` and a valid source role, plus valid targets. Instead of showing the source error, the action copies that role's rules from every tracker and replaces the named target workflows. Because the plugin can apply this to several projects in one request, an invalid identifier can cause a broad, successful and destructive write rather than a safe rejection.

**How I verified it**

Read the plugin condition and fetched the supported Redmine 7.0 controller source. Redmine's finder returns `nil` for a missing id and uses the same `nil` for `any`; the plugin condition is `(@source_tracker.nil? && @source_role.nil?)`, so exactly one missing record is accepted. This was source-level verification; it was not executed because no Redmine host is present.

**Suggested direction**

Validate each source parameter independently before resolving it: accept `any` explicitly, otherwise require an all-digit id that resolves to a record. Keep the legitimate combinations (specific/specific, any/specific, specific/any), but reject a supplied id that did not resolve. Add controller regression examples for an invalid tracker with a valid role and an invalid role with a valid tracker, asserting no workflow or scope rows change.

**Resolution:** Fixed as suggested, in `#duplicate`. `invalid_copy_selection?` now runs
before anything is written and rejects a source tracker or role that was supplied
in any shape other than `any` and did not resolve to a record — the shape is
checked as well as the record, because core resolves the id with `to_i`, so
`'12abc'` silently meant tracker 12. The three legitimate readings of `any` are
unchanged and now have examples of their own. The message is core's
`error_workflow_copy_source` rather than the plugin's
`error_workflow_copy_source_project`, because the tracker or role is what is
wrong, not the project.

One thing was wider than the finding says, and is fixed too: the check runs for
**every** request, not only for one that names a project. The finding places the
defect in the project branch, but `#duplicate` hands a request with no project
parameter to core — and the copy form's target project selector is a `multiple`
select, which submits nothing at all when nothing is selected. So the unguarded
path was reachable from the plugin's own form, not only from a hand-built
request. `spec/controllers/workflows_controller_spec.rb` covers it as
"rejects a source tracker id that does not exist when no project is named".

Verified red on the old code: four of the new examples failed against `db381fc`
(`999999` as a tracker, `999999` as a role, `'<id>abc'` as a tracker, and the
no-project-named case), each having written a row rather than rejecting the
request. Green after the change, with the full suite at 577 examples / 0 failures
on Redmine 5.1, 6.1 and 7.0 on PostgreSQL 16, and RuboCop clean.

### F02 — Mixed valid and invalid target tracker/role ids are silently applied partially

- **Status:** fixed
- **Severity:** minor
- **Confidence:** confirmed
- **Category:** correctness, ux
- **Where:** `lib/redmine_project_workflows/patches/workflows_controller_patch.rb:132-180`; upstream Redmine 5.1/6.1/7.0 `WorkflowsController#find_sources_and_targets`
- **Invariant touched:** none

**What is wrong**

The plugin strictly validates project targets in `validated_target_project_ids`, but target trackers and roles still come from core's `where(id: values).to_a`. Unknown, malformed and duplicate values are discarded. Validation checks only whether the resulting arrays are blank, so a mixed selection such as one real tracker plus one deleted tracker is accepted and applied to the real tracker without telling the administrator that part of the requested selection was ignored.

**Why it matters**

An administrator opens the copy form, one selected tracker or role is deleted before submission (or a proxy/client sends a malformed extra value), and the request still reports success. Only the surviving targets are changed. With several projects selected, the success notice can conceal a partially applied bulk operation and leave project workflows inconsistent with the administrator's intended selection.

**How I verified it**

Compared `find_sources_and_targets` in upstream Redmine 7.0 with the plugin's `duplicate` action and `validated_target_project_ids`. Only project target ids are checked back against submitted values; tracker and role relations silently omit missing ids, and the action proceeds whenever at least one remains. This was source-level verification; it was not executed because no Redmine host is present.

**Suggested direction**

Resolve target tracker and role selections with the same exact-set validation already used for project targets: strict decimal shape, de-duplication, one query, and rejection when any submitted id is absent. Preserve the copy form with the submitted selections and a translated validation error, and add regression tests proving that mixed valid/invalid selections write nothing.

**Resolution:** Fixed as suggested, in the same `invalid_copy_selection?` guard.
`unresolved_target_ids` subtracts the ids core actually resolved from the ids the
request submitted, de-duplicated first, and any remainder rejects the request —
so the rule the target *projects* have been held to since WP0 now covers all four
selectors. No extra query: the comparison uses the records
`find_sources_and_targets` had already loaded. A malformed id is rejected by the
same subtraction, because `where(id: '2abc')` resolves to record 2 and `'2abc'`
is not `'2'`.

The error is a new translated key, `error_workflow_copy_target_tracker_or_role`
("One or more selected target trackers or roles do not exist."), added to all
eight locale files and translated in each — parallel to the existing
`error_workflow_copy_target_project`, and distinct from it because "you selected
nothing" and "what you selected is gone" are different things to be told. The
form is rendered back with the selections that did resolve, which is what the
existing target-project branch does.

Verified red on the old code: three of the new examples failed against `db381fc`
(a missing target tracker id, a missing target role id, and a malformed target
tracker id), each having written a row and redirected with the success notice.
Green after the change; a fourth example pins that the same id submitted twice is
still one selection and still succeeds. Same evidence as F01: 577 examples / 0
failures on 5.1, 6.1 and 7.0 on PostgreSQL 16, RuboCop clean.
