## Summary

The 0.1.1 repairs to the administration matrix are sound: a cell left at
*(No change)* survives a save, an ordinary Save no longer hands an inheriting
project an own empty workflow, a multi-project save is one transaction, and a
malformed submission is rejected rather than raising. Two things were found
that the earlier reviews had not. One is a rule this repository states
absolutely and the code broke: scopes were created with `insert_all`, which is
confined to the two rule writers — and which skips conflicting rows silently,
so the method reported creating rows it had not created. The other is a race:
whether a project runs its own workflow was read without a lock and acted on
afterwards, so a save running beside a *return to the generic workflow* could
leave rules in the table under no scope — invisible to the resolver, on a save
that had reported success.

### F01 — `ScopeWriter` creates scopes with the forbidden `insert_all`, and miscounts what it created

- **Status:** fixed
- **Severity:** blocker
- **Confidence:** confirmed
- **Category:** correctness
- **Where:** `lib/redmine_project_workflows/services/scope_writer.rb` (`create_scopes`)
- **Invariant touched:** INV-2, and the forbidden-constructs table in `CLAUDE.md` (gate G7)

**What is wrong**

`ScopeWriter.create_scopes` uses `ProjectWorkflowScope.insert_all`, which
`CLAUDE.md` permits only inside `TransitionWriter` and `PermissionWriter`. The
comment at the call site argues a local exception; a comment cannot lift a
repository-level rule, and G7 greps for exactly this.

It is not only formal. `insert_all` skips conflicting rows by default, while
the comment claims a concurrent duplicate would raise `RecordNotUnique`. So two
concurrent *give own workflow* operations can both report that every scope was
created, although one insert was skipped in whole or in part.

**Why it matters**

Two administrators press *give own workflow* for the same (project, tracker,
role) at the same moment. Both are told the scope was created. The second one's
`enable` then goes on to clear the rules of that combination and copy the
generic workflow over them — over rules the first administrator had just
produced — while reporting a count that includes a row it never wrote.

**How I verified it**

Read-only: the call site against the documented rule, and `insert_all`'s
documented conflict handling against the comment's claim. Not executed.

**Suggested direction**

Restore compliance first — validated model creation — or record a formally
approved bulk-scope boundary in the invariants or an ADR. Then have the method
report only the combinations it actually inserted, and add a
concurrency/idempotency test.

**Resolution:** Fixed by restoring compliance rather than by widening the rule:
`create_scopes` builds one `ProjectWorkflowScope` per combination and calls
`save!`, so the model's validations run, and it returns the combinations whose
row this call actually inserted. `enable` now clears and re-copies rules for
that returned list rather than for the list it set out to create, which is the
half of the finding that damages data. A duplicate arrives as either
`RecordInvalid` (the uniqueness validation's SELECT saw the winner) or
`RecordNotUnique` (the winner committed between that SELECT and this INSERT);
both mean "somebody else got here first" and are the only failures swallowed —
any other `RecordInvalid` is re-raised. Each row is written inside a savepoint
(`requires_new: true`), because on PostgreSQL a failed statement makes every
later statement of the same transaction fail too, and one lost race must not
take the rest of the selection with it.

The cost is one round trip per combination where 0.1.1 made one per thousand,
on an action whose largest selection is projects × trackers × roles. That is
accepted here and recorded in `docs/DECISIONS.md` as an open question for Jan:
whether a formally approved bulk boundary for this table should exist at all
(the reviewer's second option), which is an ADR conversation rather than a code
decision.

Tests, all red on `ed4073d`: `spec/plugin_conventions_spec.rb` greps `app/`,
`lib/` and `db/` and fails unless `.insert_all` appears in the two rule writers
and nowhere else; `spec/services/scope_writer_spec.rb` covers the scope that
appears after the check (0 created, the winner's rules untouched — the old code
reported 1 and overwrote them), a row that loses the narrow race while the rest
of the selection still goes in, and a row the model rejects for any other
reason, which raises instead of being reported as somebody else's.

### F02 — A concurrent return to the generic workflow can leave rules with no scope

- **Status:** fixed
- **Severity:** minor
- **Confidence:** probable
- **Category:** concurrency
- **Where:** `lib/redmine_project_workflows/services/matrix_scope.rb` (`writable_pairs`),
  `lib/redmine_project_workflows/services/scope_writer.rb` (`return_to_inheritance`)
- **Invariant touched:** INV-3

**What is wrong**

`writable_pairs` checks whether a scope exists with an ordinary, unlocked
`pluck`. The scope's audit columns are then stamped and only afterwards are the
workflow rules written. Between the check and the write another transaction can
delete the scope.

**Why it matters**

A possible order:

1. Save transaction A sees the scope.
2. Transaction B performs *return to generic* and deletes the rules and the scope.
3. A stamps zero scopes but writes its project rules anyway.
4. The project rules exist physically, but with no scope the resolver ignores them.
5. The save reports success although the change never took effect.

Recoverable but inconsistent dead data, and it touches both transitions and
permissions.

**How I verified it**

Read-only; classified *probable* rather than confirmed because no
two-connection test was run.

**Suggested direction**

Lock the exact scope rows with `FOR UPDATE`, derive the writable pairs from
those locked rows, and make *return to generic* take the same locks in the same
order. Add deterministic two-connection tests for both commit orders.

**Resolution:** Fixed as suggested. `ScopeWriter.existing_combinations` takes a
`lock:` keyword; `MatrixScope#writable_pairs` passes it, and both rule writers
already ask inside the transaction that then writes the rules, so the check and
the write are now one decision. `return_to_inheritance` and `clear_rules` take
the same locks before either delete, which is also what keeps the two from
deadlocking: every caller takes scope rows before workflow rows.

The lock is taken by primary key in a second statement, in id order, and what
that statement returns is the answer rather than what the first one found. A
row this transaction had to wait for, and which the transaction it waited for
deleted, is simply absent from it — that is what makes the save report the pair
skipped instead of writing under a scope that is gone. By primary key rather
than by the (project, tracker, role) predicate because InnoDB would otherwise
take gap locks over a mostly empty range; in id order because two callers must
take the same locks in the same order.

`spec/services/workflow_concurrency_spec.rb` is new and has both halves. Three
single-connection examples assert the shape — the `FOR UPDATE` on
`project_workflow_scopes` precedes the first write to `workflows` for a project
save and for a return to the generic workflow, and is *not* taken for a generic
write, which has no scope to lock. Two examples run a real second connection
(the group turns off transactional fixtures) and assert the outcome for both
commit orders: the save first, then the return, which must leave no rule
behind; and the return first, then the save, which must be refused and counted
as skipped. Four of the five are red on `ed4073d` — the fifth is the guard
against locking a generic write, which the old code also satisfied, by doing
nothing at all.
