## Summary

The external review is largely right; ten of its eleven findings stand, three
of them for a heavier or different reason than stated. What it could not do was
run anything, and that is where these six additional findings come from —
mostly by asking which of Redmine's *own* queries read the `workflows` table
without knowing that projects exist.

The most useful of these is F01: Redmine already has a workflow overview page,
the plugin does not patch it, and its counts become wrong the moment an
override exists. That is both a defect and the cheapest place to put the
inventory the external review asks for as new work.

F04 is the only finding that makes the plugin actively worse on a supported
version: on Redmine 6.0 and later the project selector aborts the page's
JavaScript initialisation.

### F01 — The workflow summary page counts project rules as generic

- **Status:** open
- **Severity:** major
- **Confidence:** confirmed
- **Category:** correctness, ux
- **Where:** core `app/controllers/workflows_controller.rb:27-31`, not patched by `lib/redmine_project_workflows/patches/workflows_controller_patch.rb`
- **Invariant touched:** INV-4

**What is wrong**

Redmine has a summary page at `/workflows`, reachable from the "Summary" button
on every workflow screen. It counts with
`WorkflowTransition.group(:tracker_id, :role_id).count` — no `project_id`
filter. The plugin patches `edit`, `update`, `permissions`, `update_permissions`
and `duplicate`, but not `index`.

**Why it matters**

As soon as one project override exists, project rows are counted into the
generic totals. The red "0" marker that tells an administrator a workflow is
unconfigured becomes unreliable, and clicking a count opens the generic matrix
regardless of which rows produced it.

There is an opportunity attached: the external review asks for a new overview
tab. This page already is that tab, with routes, styling and a place in the
action menu. Repairing it and adding an inventory alongside is cheaper than a
new navigation concept, and stays Redmine-idiomatic by construction.

**How I verified it**

One generic rule gives a count of 1; adding one project rule for the same
tracker and role makes the same page report 2, while there is still exactly one
generic rule. `spec/characterization/known_issues_spec.rb`.

**Suggested direction**

Count per scope, with a project selector defaulting to generic so the page
behaves as before for installations that do not use the plugin.

**Resolution:** _(open — WP3)_

### F02 — `Tracker#issue_status_ids` ignores `project_id`

- **Status:** adjusted
- **Severity:** minor (reported as major; lowered after working out the fix)
- **Confidence:** confirmed
- **Category:** correctness
- **Where:** core `app/models/tracker.rb:113-117`, and its two call sites in `app/models/issue.rb`
- **Invariant touched:** INV-4

**What is wrong**

Core computes a tracker's statuses with `WorkflowTransition.where(tracker_id: id)`
and no project filter, so a status used only in one project's workflow appears
in the tracker's global list.

**Why it matters**

The obvious reading is that project data leaks into a global list. Working out
the repair showed the direction of the error is the safe one. Both call sites
are in `Issue`: one decides on a tracker change whether the current status may
be kept, the other picks the initial status in `new_statuses_allowed_to`.
Narrowing the list to generic rules would make an issue in a project whose own
workflow uses an extra status **lose** that status on a tracker change. Too
wide is a nuisance; too narrow costs data.

**How I verified it**

With only a project rule present and no generic rule at all,
`Tracker#issue_status_ids` returns both statuses.
`spec/characterization/known_issues_spec.rb`. The call sites were read in
Redmine 7.0-stable at `issue.rb:404` and `issue.rb:1101`.

**Suggested direction**

Leave the tracker method as a global union and make the two `Issue` call sites
project-aware instead — the project context is known at both.

**Resolution:** severity lowered from major to minor and the direction of the
fix inverted, before any code was written. The characterization example is to be
rewritten to the project-aware behaviour rather than inverted. Scheduled in WP2.

### F03 — Copying a role or tracker leaves project workflows behind

- **Status:** open
- **Severity:** minor
- **Confidence:** confirmed
- **Category:** correctness
- **Where:** `lib/redmine_project_workflows/patches/workflow_rule_patch.rb:95-97`; core `app/models/role.rb:281-283` and `app/models/tracker.rb:147`

**What is wrong**

`Role#copy_workflow_rules` and the tracker equivalent go through
`WorkflowRule.copy` → `copy_one`, and the plugin has pinned `copy_one` to
`project_id = nil`.

**Why it matters**

A role copied from an existing one gets the generic workflow but none of the
project overrides, silently. In an installation that uses project workflows the
copy is not a copy.

**How I verified it**

Read the call chain in Redmine 7.0-stable and the plugin patch. Not executed —
this one is a reading, and I am marking it as such rather than implying
otherwise.

**Suggested direction**

Carry project rules, and their scopes once those exist, so a copied role is a
working copy. A checkbox in the form would need two more Deface anchors.

**Resolution:** _(open — WP2)_

### F04 — The empty toggle span breaks JavaScript on Redmine 6.0 and later

- **Status:** fixed
- **Severity:** major
- **Confidence:** confirmed
- **Category:** ui, portability
- **Where:** `app/views/redmine_project_workflows/_project_selector.html.erb:7`

**What is wrong**

The partial renders `<span class="toggle-multiselect icon-only"></span>`. On
5.1 that was right: the icon came from CSS. From 6.0 the icons are SVG sprites
and core renders `sprite_icon('')` inside the span. Core's
`toggleMultiSelectIconInit()` then calls
`updateSVGIcon($(this).find('svg')[0], iconType)`, which is `undefined` for the
plugin's span, and `element.getElementsByTagName` throws.

**Why it matters**

The exception is raised inside `$(document).ready`, so everything registered
after `toggleMultiSelectIconInit()` never runs on that page. This is why the
README's claim that 6.0 and 6.1 "should also work" is wrong as written.

**How I verified it**

Two ways. In the rendered page of a running Redmine 7.0.0 there are three
`toggle-multiselect` spans: two from core with an `<svg>`, one from the plugin
without; on 5.1 none of the three has one, which is why it is harmless there.
Then in Chromium, with core's own jQuery and the two functions taken verbatim
from `application-legacy.js`:

```
exception in init : TypeError: Cannot read properties of undefined (reading 'getElementsByTagName')
code after init   : not reached — initialisation aborted
```

`spec/characterization/known_issues_spec.rb` asserts the markup half.

**Suggested direction**

Render the sprite when the host provides `sprite_icon`, with a `respond_to?`
fallback for 5.1, behind the one version helper.

**Resolution:** fixed in WP0. `app/views/redmine_project_workflows/_project_selector.html.erb`
now calls `project_workflows_toggle_multiselect_tag`, the first entry in the
single version helper `RedmineProjectWorkflows::VersionHelper`: it renders
`sprite_icon('')` where the host provides it and an empty span on 5.1, so the
plugin's span matches core's on whichever version it is running on. The
characterization example was replaced by two assertions in
`spec/integration/deface_overrides_spec.rb` — one per screen — that check every
`.toggle-multiselect` span on the rendered page, in whichever direction the
host requires. Both fail on the old code on 6.1 and 7.0.

### F05 — Patches are applied in `after_initialize` rather than `to_prepare`

- **Status:** adjusted
- **Severity:** minor
- **Confidence:** probable
- **Category:** code-quality
- **Where:** `init.rb:19-22`

**What is wrong**

`apply_patches` hangs off `after_initialize`. In development with code
reloading, `Issue`, `WorkflowsController` and `WorkflowsHelper` are reloaded
without the prepends.

**Why it matters**

The plugin stops working part-way through a development session, in a way that
looks like a bug in the feature being worked on. Redmine's convention is
`Rails.application.config.to_prepare` with an idempotent guard.

**How I verified it**

Read `init.rb` and Redmine's plugin loader. Not reproduced in a live reloading
server — marked probable rather than confirmed for that reason.

**Suggested direction**

Move to `to_prepare`; keep the prepend guard the loader already implies.

**Resolution:** the reported defect does not exist, and the suggested direction
would have caused a much worse one. Both were established by reading
`lib/redmine/plugin_loader.rb` and `railties/lib/rails/application/finisher.rb`
and then by booting the plugin in a real host on 5.1 and 7.0.

Redmine's `PluginLoader` loads every plugin's `init.rb` from inside a
`to_prepare` block, so `init.rb` is re-executed after every reload. On a reload
the `:after_initialize` load hook has already fired, so
`config.after_initialize` runs its block immediately — on the classes the
reload has just produced. The patches were therefore never lost. Verified:
`Issue.ancestors.include?(IssuePatch)` is true in a freshly booted host on the
old code.

`config.to_prepare` would have been actively wrong.
`Rails::Application::Configuration#to_prepare` only appends to
`config.to_prepare_blocks`, and the initializer that wires that array into the
reloader (`:add_to_prepare_blocks`) has already run by the time any plugin's
`init.rb` is loaded. The block is never called: the change was written, and a
freshly booted 7.0 then reported every patch missing while the suite stayed
green, because `spec/spec_helper.rb` re-applied the patches itself.

What did change in WP0: `apply_patches` is called in the body of `init.rb`,
which is the `to_prepare` window Redmine already provides, with an idempotent
`prepend_once` guard. `config.after_initialize` was not wrong, but it described
the opposite of what happens and registered one more `:after_initialize` load
hook on every reload. The masking fallback in `spec/spec_helper.rb` was removed,
so `spec/plugin_conventions_spec.rb` now fails the whole suite if the host boot
does not install the plugin. Severity lowered from minor to none as a defect;
`CLAUDE.md`'s forbidden-constructs table was corrected, because it prescribed
the broken form.

### F06 — Row and column bulk actions skip mixed cells

- **Status:** open
- **Severity:** minor
- **Confidence:** confirmed
- **Category:** ux
- **Where:** `lib/redmine_project_workflows/patches/workflows_helper_patch.rb:47-70`; core `app/views/workflows/_form.html.erb:5, 14, 26`

**What is wrong**

Core already puts a `toggle_checkboxes_link` in every row and column header of
the transitions matrix, selecting on `.old-status-N` / `.new-status-N`.
`transition_tag` puts those classes on checkbox cells but not on the `<select>`
it renders for mixed values.

**Why it matters**

Row and column actions therefore exist but silently skip exactly the cells that
need them — which is the manual work the external review describes as a UX
problem to be solved with new controls. Adding the same classes and data
attributes to the select branch makes core's existing buttons work on mixed
selections, with no new UI.

**How I verified it**

Read `transition_tag` against core's `_form.html.erb` in 5.1 and 7.0 (identical
in both) and the selector in `toggleCheckboxesBySelector`.

**Suggested direction**

Same classes and data attributes on both cell types. Then add explicit
Yes / No / Unchanged actions, because toggling is not the same as setting to No
and setting to No is the case with the manual work.

**Resolution:** _(open — WP5)_
