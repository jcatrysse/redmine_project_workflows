Overall assessment

The new version is a substantial improvement over the version reviewed on 2026-08-28. It is not merely more documented: it directly addresses nearly every prior finding.

Major improvements include:

    Generic workflow writes now use plugin-owned coordination rows, closing the previously documented duplicate-row race.

    Large administration writes now have server-side ceilings and client-side confirmation thresholds.

    Most project-specific behavior was moved off Redmine’s core workflow screens into plugin-owned administration screens.

    Deface is now constrained to a tested major-version range.

    Compatibility information is centralized and exposed through an administrator diagnostics facility.

    The graph role-selection bug from the previous review was fixed by rejecting any unresolved role ID, including a mixture of valid and invalid IDs.

    Permission names were changed to avoid a demonstrated collision with another plugin, and a migration attempts to preserve existing grants safely.

    Backup, restore, uninstall, upgrade, and previous-release rehearsal tooling now exists.

The application runtime looks materially safer. I found no confirmed authorization bypass, injection vulnerability, XSS flaw, CSRF bypass, cross-project write, or secret exposure.

However, the new backup and restore subsystem introduces two High-severity failure-consistency issues:

    A backup is assembled through separate, unlocked scope and rule queries and can therefore be internally inconsistent if workflows change during export.

    Restore is not atomic. It creates or clears all selected scopes before restoring rules combination by combination. A crash after preparation can leave workflows owned but empty; a normal retry then skips those scopes by default.

Those issues undermine the new claim that destructive uninstall is safely reversible. The plugin also still permits writes on an unverified or drifted Redmine version after warning the administrator.

The README continues to state explicitly that the plugin is alpha and must not be used in production.
The project’s own release criteria likewise say the production-readiness criteria remain incomplete.

ID: BACKUP-001

Severity: High
Confidence: Confirmed

Location:

    lib/redmine_project_workflows/services/workflow_backup.rb

        document, lines 39–51.

        scope_rows, lines 97 onward.

    lib/redmine_project_workflows/tasks.rb

        uninstall, lines 39–50.

    lib/tasks/redmine_project_workflows.rake

        backup and uninstall tasks, lines 10–31.

Problem

A workflow backup is not taken from a transactionally consistent snapshot.

WorkflowBackup.document queries scopes and rules separately:

scopes = scope_rows
rules = rule_rows

and then combines the two results.

No transaction, database snapshot, or workflow coordination lock spans those queries.

The uninstall task builds this document and subsequently reverses migrations, again without preventing workflow writes between the export and destruction.
Evidence

The backup format depends on the invariant that scope decisions and their project-specific rules describe one logical instant. A scope without rules means “owned empty,” while absence of a scope means inheritance. Those are materially different states.

Because the two populations are queried independently, a concurrent enable, clear, inherit, or matrix save can occur between them.

The uninstall process has an even wider race:

    build backup;

    display counts;

    confirm;

    write backup;

    reverse migrations.

A project manager can change a workflow after step 1 but before step 5.
Impact

The backup can silently contain:

    a scope but only part of its rules;

    rules with no corresponding scope;

    a scope that had already been returned to inheritance;

    an old rule set combined with a new scope state;

    none of a change committed after export but before uninstall.

Restoring such a backup can change workflow permissions and status-transition behavior.

For destructive uninstall, this becomes permanent data loss because the migration reversal deletes all project-specific rules and scopes.
Scenario

A project manager saves a project workflow while an administrator runs:

RAILS_ENV=production bundle exec rake redmine_project_workflows:uninstall \
  FILE=/var/backups/project-workflows.json CONFIRM=yes

The backup reads the scope rows. The manager commits a new matrix. The backup then reads rules or completes from stale data. The uninstall subsequently deletes the live workflow. The backup is readable JSON and passes structural validation, but it does not represent any state that actually existed atomically.
Recommended fix

At minimum:

    Run WorkflowBackup.document inside a transaction using a consistent snapshot appropriate to each supported database.

    Coordinate against plugin write paths:

        acquire all relevant workflow coordination locks in deterministic order; or

        place Redmine in maintenance/read-only mode before backup and uninstall.

    For uninstall, verify immediately before migration reversal that:

        no workflow change occurred after the export;

        a durable revision/checksum still matches the exported state.

    Write the backup atomically:

        create a temporary file in the target directory;

        flush and fsync;

        validate by reading it;

        atomically rename it to the requested path.

    Document that destructive uninstall requires a maintenance window unless the code enforces exclusion itself.

A database-wide transaction alone is not sufficient if the transaction ends before migrations begin and writes can occur between export and destruction.
Regression test

Add a real two-connection test:

    start a backup;

    pause after scopes are read;

    commit a matrix change from another connection;

    finish the backup;

    assert that the operation either:

        blocked the concurrent writer;

        captured a consistent before-state;

        captured a consistent after-state; or

        aborted because the revision changed.

Add a separate uninstall integration test that attempts a workflow write between backup validation and migration reversal and proves it cannot be silently lost.
ID: RESTORE-001

Severity: High
Confidence: Confirmed

Location:

        call, lines 82–94.

        prepare, lines 119–141.

        write_one, lines 157–163.

    lib/tasks/redmine_project_workflows.rake

        restore task, lines 18–27.

    README.md

        idempotent restore claim, lines 602–632.

Problem

Restore is not atomic, and its operation ordering can make a failed restore unsafe to retry with default options.

The restore does this:

    selects every restorable combination;

    calls prepare for all combinations;

    loops over combinations and restores rules one at a time.

prepare creates missing scopes and clears rules from overwrite targets before the rule-writing loop begins.

Each subsequent write_one restores only one combination.

There is no outer transaction around the full restore.
Impact

A database error, deadlock, process termination, disk failure, deployment restart, or operator interrupt after prepare can leave many workflows as owned empty workflows.

That state is security- and availability-relevant:

    transitions may be entirely prohibited;

    fields may lose required/read-only rules;

    issues may become unable to leave their current status.

The retry behavior is particularly dangerous. By default, restore skips any combination that already has a scope. After preparation, those scopes exist, so a default retry can skip the exact workflows whose rules were never restored.

This contradicts the practical implication of the README’s statement that running restore twice is safe.

The second run may be harmless after a successful first run, but it is not necessarily a safe recovery mechanism after a failed first run.
Scenario

A restore contains 2,000 project workflow combinations.

    prepare creates all 2,000 scope rows.

    Rules are restored for the first 200 combinations.

    The database connection is lost.

    The remaining 1,800 combinations are now owned but empty.

    The operator reruns the documented restore command without OVERWRITE=1.

    The restore sees all 2,000 scope rows as existing and skips them.

The command completes without restoring the missing rules.
Recommended fix

Choose one of these transaction models:
Preferred: per-combination atomic restore

For each combination:

    begin a transaction;

    acquire its coordination lock;

    create or clear its scope;

    restore all its rules;

    restore audit metadata;

    commit.

A failed combination rolls back to its prior state. Completed combinations are safe to skip on retry.

This avoids an enormous transaction while preserving retry safety.
Alternative: whole-restore transaction

Wrap preparation, all rule writes, and audit stamping in one outer transaction. This provides all-or-nothing semantics but may create a long transaction on large installations.

Also add a durable restore journal or explicit completion marker if partial progress is intentionally supported.

The restore report should distinguish:

    completed;

    skipped because already identical;

    skipped because existing and different;

    failed;

    pending after interruption.

Regression test

Inject an exception:

    after scopes are prepared but before the first rule write;

    after the first successful combination;

    during permission restoration;

    during audit stamping.

After each failure, assert that:

    no combination is left unintentionally empty;

    a default retry restores all remaining data correctly;

    successfully preexisting workflows are unchanged;

    OVERWRITE=1 does not cause partial destructive clearing.

This should run on PostgreSQL, MySQL, and MariaDB.

Problem

The compatibility subsystem now detects and reports unverified or drifted Redmine versions, but does not apply a safety policy to workflow writes.

The design explicitly chooses not to refuse operation on an unsupported host.

That avoids bricking Redmine during an upgrade, which is a valid operational concern. However, a detected :drifted or :unmeasured state can still execute:

    issue workflow evaluation;

    generic workflow writes;

    project workflow writes;

    scope changes;

Impact

The plugin can knowingly operate in a state where:

    copied Redmine core methods differ;

    a required method is missing;

    a method newly added by Redmine is shadowed;

    source cannot be measured.

Because workflow logic is authorization logic, warning-only behavior is insufficient for unrestricted writes.
Scenario

    Always allow Redmine to boot.

    Always allow the diagnostics page.

    Allow reads if they can be performed safely.

    Disable workflow-mutating plugin actions when state is:

        drifted;

        unmeasured;

        missing a required dependency.

    Allow an explicit administrator acknowledgment tied to:

Problem

The new administration matrix controller does not validate tracker and role selection with the same completeness used by the copy and graph paths.

find_selection sends request values directly to:

klass.where(id: ids).to_a

and returns whatever records resolve.

Therefore:

    a deleted ID is silently dropped;

    a mixed valid and invalid selection silently narrows;

    adapter coercion can accept malformed numeric strings depending on the database;

    the subsequent write operates on the surviving records and reports success.

By comparison:

    copy selections explicitly detect unresolved target IDs;

    graph selections reject any unresolved requested role ID.

    scope routes validate ID shape and require every requested record to resolve.

Impact

This is administrator-only and does not widen access. The danger is partial configuration:

    an administrator thinks several roles or trackers were updated;

    one stale or malformed ID is silently ignored;

    the surviving subset is written;

    the success message does not identify the partial selection.

Workflow configuration then differs from operator intent.
Scenario

A saved browser form names tracker IDs 3 and 8. Tracker 8 is deleted before submission. The PATCH writes tracker 3, silently drops tracker 8, redirects, and reports success.
Recommended fix

Replace find_selection with exact resolution:

    normalize to unique strings;

    handle the single all keyword;

    reject mixed all plus explicit IDs unless explicitly supported;

    require /\A\d+\z/;

    query the IDs;

    compare all submitted values with resolved IDs;

    render a corrective error or 404 before a write if any are unresolved.

Extract this into one reusable selection resolver used by:

    administration matrices;

    copy;

    graph;

    scope actions.

That would reduce both inconsistency and duplicated validation logic.
Regression test

For both tracker and role parameters, test:

    valid ID;

    invalid ID;

    valid plus invalid;

    deleted record after form display;

    01;

    1e5;

    12abc;

    nested hash;

    duplicate IDs;

    all;

    all mixed with explicit IDs.

Assert that no workflow rows change when any requested selection is invalid.

Problem

Backup writing uses a direct File.write to the final path and relies on the process umask for file permissions.

The documentation correctly says the file contains project, tracker, role, and status names and should not be world-readable.

However, the implementation neither creates the file with restrictive permissions nor writes atomically.
Impact

Depending on the service account’s umask:

    the file may be readable by unintended local users;

    a process interruption may leave a truncated final backup;

    an existing backup overwritten with FORCE=1 may be destroyed before the replacement is durably complete.

The uninstall task reads the file back, so ordinary truncation is likely detected before migrations. This lowers severity, but explicit file safety would be preferable for a recovery artifact.
Scenario

Redmine is operated under a service account with umask 0022. The generated JSON backup receives mode 0644 in a shared backup directory, exposing internal project and role names to other local accounts.
Recommended fix

    Create a temporary file in the same directory with mode 0600.

    Write, flush, and fsync.

    Validate from that file.

    Atomically rename it into place.

    If overwriting, preserve the previous file until the new file is durable.

    Optionally allow an explicit mode parameter for environments with managed backup permissions.

Regression test

Assert that:

    a newly created backup has mode 0600;

    simulated interruption does not replace an existing valid backup;

    overwrite performs an atomic replacement;

    malformed or truncated temporary files never become the final backup.

Architecture Assessment
What is now well designed
1. Plugin-owned administration screens

This is the most important maintainability improvement.

Previously, project-specific behavior was attached to Redmine’s core administration pages with many Deface overrides and a large controller patch. The new ProjectWorkflowRulesController owns:

    project selection;

    project-aware summary;

    transition matrix;

    permission matrix;

    copy screen;

    authorization callback ordering.

Redmine’s generic administration screen can remain generic. That is a cleaner ownership boundary and substantially reduces upgrade risk.
2. Unified write coordination

The generic and project populations now have a common conceptual lock key:

(rule_type, project-or-generic, tracker, role)

Project writes lock scope rows; generic writes lock plugin-owned coordination rows.

The MySQL/MariaDB snapshot analysis shows serious attention to real adapter behavior rather than optimistic Rails-looking code.
3. Explicit write budgets

The write budget is:

    calculated server-side;

    expressed in workflow-rule units;

    configurable;

    checked before large matrix transactions;

    applied to bulk workflow enable operations.

This is preferable to relying only on a JavaScript confirmation.
4. Compatibility as a first-class object

The compatibility manifest consolidates previously scattered assumptions and supports diagnostics.

The digest service now watches:

    instance-method replacements;

    singleton-method replacements;

    plugin-owned copied controller/helper bodies;

    called-but-not-shadowed Redmine dependencies.

5. Release engineering

The repository now has explicit release criteria, migration reversal, upgrade rehearsal, prior-release upgrade rehearsal, uninstall backup, and restore tooling.

This is unusually mature for a Redmine plugin at version 0.1.6.
What remains fragile
1. Core workflow method replacement

Even with better drift detection, the plugin continues to replace behavior at the heart of Redmine’s issue authorization and workflow system.

The diagnostics reduce surprise; they do not eliminate semantic incompatibility.
2. Core workflows table modification

The design still adds project_id and indexes to a core Redmine table. That provides good integration with Redmine’s existing STI workflow models, but it remains the plugin’s largest upgrade and uninstall coupling.
3. Backup/restore orchestration

The underlying serializers and rule whitelisting are good, but the transaction boundaries are currently weaker than the safety claims around destructive uninstall.
4. Selection validation duplication

Project, tracker, role, graph, copy, and scope selections have several different resolvers. Most are now strict, but the administration matrix remains inconsistent. A single exact-selection abstraction would reduce this risk.

Simplification Opportunities
1. One exact selection resolver
Current complexity

Simpler approach

Create a single resolver that accepts:

    relation or server-built allowed records;

    submitted values;

    allowed keywords;

    scalar/list rules;

    whether empty is valid.

Return:

SelectionResult.new(records:, keywords:, invalid_values:)

Why safer

    fixes the remaining partial matrix selection bug;

    makes malformed-ID handling consistent;

    reduces duplicated comments and tests;

    prevents future controller paths from forgetting exact resolution.

2. Make restore per-combination transactional
Current complexity

Restore has a global prepare phase followed by individual writes.
Simpler approach

For each scope:

validate -> lock -> prepare -> write rules -> stamp audit -> commit

Why safer

    natural retry semantics;

    no global owned-empty intermediate state;

    failure affects at most one combination;

    avoids one enormous transaction.

Components affected

    WorkflowRestore

    restore specs

    rake output/reporting.

3. Introduce a workflow configuration revision
Current complexity

Consistency is inferred through row locks and table contents.
Simpler approach

Maintain one monotonically increasing revision for workflow configuration changes.

Use it to:

    mark backups;

    detect changes during export;

    detect changes between uninstall export and destruction;

    provide stale-form detection;

    improve audit correlation.

Why safer

It gives backup/uninstall a cheap, durable consistency check without locking every project workflow for the entire operator confirmation interval.
Components affected

    one migration/model;

    write coordinator;

    backup document;

    uninstall task;

    diagnostics.

4. Generate compatibility and support documentation from the manifest
Current complexity

The manifest is centralized, but README, CI, release criteria, and comments still repeat version facts.
Simpler approach

Add a check or generator that compares:

    manifest minors;

    CI matrix;

    README compatibility table;

    Ruby versions;

    databases.

Why safer

It reduces the chance that the new compatibility object becomes merely one more source of truth.

Final Approval Decision

    Would I personally approve this plugin for deployment on a production Redmine instance today?

Not yet.

The answer is much closer to “yes” than it was in the previous review. The normal runtime workflow logic, authorization, concurrency handling, scalability boundaries, dependency constraint, compatibility diagnostics, plugin coexistence, and administration architecture are all materially improved.

I would still withhold production approval because the newly introduced recovery mechanism is not yet reliable under concurrency or interruption. A destructive uninstall backup must represent a consistent state, and a restore must not be able to leave hundreds of workflows owned but empty in a way that a normal retry skips. Those are realistic production failure modes with direct workflow-authorization and availability consequences.

Once BACKUP-001 and RESTORE-001 are fixed and independently tested across the three supported databases, I would reassess the plugin as READY WITH FIXES, subject to the project’s remaining release and real-installation soak criteria.
