### F01 — The drawing ignores core's fallback to the tracker's default status, so on a stock Redmine every status reads as unreachable

- **Status:** fixed
- **Severity:** major
- **Confidence:** confirmed
- **Category:** correctness
- **Where:** `lib/redmine_project_workflows/services/workflow_graph_query.rb:35`,
  `lib/redmine_project_workflows/services/workflow_graph_ranking.rb:65`,
  `spec/services/workflow_graph_layout_spec.rb:56`
- **Invariant touched:** none

**What is wrong**

The drawing's entry point is core's *new issue* pseudo-status, stored as
`old_status_id = 0`, and reachability is computed from that node alone. But
`old_status_id = 0` is not the whole of how Redmine decides a new issue's status.
`Issue#new_statuses_allowed_to` asks `IssueStatus.new_statuses_allowed` with
`status_id = status.try(:id) || 0` (`app/models/issue_status.rb:66`) and then, two
lines further on, adds a fallback: `statuses << default_status if include_default
|| (new_record? && statuses.empty?)` (`app/models/issue.rb:1123`). So when no rule
comes out of node 0, a new issue still gets one status — the tracker's default.

Redmine's own `redmine:load_default_data` seeds **no** `old_status_id = 0` row.
That is not an unusual configuration; it is the shipped one. Every installation
that has never hand-edited the *New issue* row of the workflow matrix is in it.

**Why it matters**

On a Redmine with default data, opening *Workflow diagram* for Bug shows: a lone
*New issue* pill above a dotted line, all six statuses below it in dashed boxes,
thirty arrows collapsed into an unreadable bundle underneath, and the *What to
look at* section reading

> **Cannot be reached from a new issue:** New, In Progress, Resolved, Wacht op
> antwoord van de klant, Closed, Rejected

(the fourth status is Redmine's *Feedback*, renamed in this fixture to a long name
so that the text wrapping was exercised at the same time)

which is false. A new Bug in that same installation is created with status *New*,
and from *New* every other status is reachable. The one diagnostic the package
exists to provide — "these statuses are unreachable, that is a defect in your
workflow" — fires on everything, on the configuration a new user is most likely
to have, and the drawing degenerates at the same time. It is the worst possible
first impression for a feature built to answer an ex-Jira user's objection.

**How I verified it**

Built a Redmine 7.0-stable host with `redmine:load_default_data`, seeded two
projects, and opened the screen in Chromium. Then, in `rails runner` on that same
database:

```
new-issue rows (old_status_id=0): 0
total generic transitions:        144
distinct old_status_id:           [1, 2, 3, 4, 5, 6]
tracker default status:           "New"
new issue offers:                 ["New"]
```

Screenshot of the degenerate drawing kept at `/tmp/pw/wp9/02-graph-union.png`
during the session. Inserting one `old_status_id = 0` rule for the two roles and
reloading turned the same screen into seven proper columns with
*"Every status in this workflow can be reached from a new issue and has a way
out."* — which isolates the cause exactly.

The suite does not see this because every graph the layout specs construct has an
edge out of the entry node; `spec/services/workflow_graph_layout_spec.rb:56` says
so in its own comment ("A -> B -> C, plus the entry node into A"). There is no
example for a workflow with no entry rule at all, which is the shipped shape.

**Suggested direction**

Model the fallback where core models it. When the selected roles have no rule out
of node 0 for this tracker, the tracker's `default_status` is where a new issue
starts, so the graph should carry an edge from the entry node to it — drawn or
labelled so that a reader can tell "this is Redmine's fallback" from "somebody
configured this", because the two are genuinely different facts about the
workflow. Reachability, the band and the diagnostic then all follow from the same
correction rather than needing three. A regression example for a workflow with no
row-0 rule belongs in `workflow_graph_query_spec.rb`, and one in the layout spec
for the shape it produces.

**Resolution:**

Fixed on `claude/dev`. Reproduced first: on a Redmine 7.0 host with
`redmine:load_default_data`, `WorkflowTransition.where(old_status_id: 0).count`
is **0** while the tracker's `default_status` is *New*, so the drawing put every
status in the band. `Services::WorkflowGraphQuery#fallback_status` now returns
`@tracker.default_status` when — and only when — no row leaves the entry node,
and `#with_fallback` puts it in the edge list as an `Edge` carrying
`fallback: true`. It is drawn as a **dotted** arrow (`stroke-dasharray="2 3"`,
against the conditional arrow's `5 3`), it carries its own legend sentence
naming it as Redmine's behaviour rather than a rule, and the table's condition
cell says *Redmine's own fallback* instead of *anyone*.

Three consequences, each deliberate and each with an example: the fallback's
target counts as **mentioned** (so it is not filed under "not used by the
selected roles", where the one status every new issue meets does not belong);
`Result#empty_workflow?` now counts `stored_edges`, so Redmine having a default
cannot make an own *empty* workflow read as one somebody filled in (INV-3); and
`WorkflowGraphLayout#drawn_status_nodes` keeps the fallback's target on an
otherwise empty workflow, so that drawing is now two boxes and one dotted arrow.

Deliberately narrow, and said in the code: only a workflow with *no* rule out of
the entry node gets the arrow. Core's real condition is that the list came back
empty *for the reader*, so a workflow whose only entry rules are author- or
assignee-only also falls back for everybody else — but the drawing has no reader
to judge a condition against, and an arrow beside a rule already pointing at the
same status would say one move twice.

Seven new examples in
`spec/services/workflow_graph_query_spec.rb` ("core's own fallback for a new
issue"), and the controller's own-empty example rewritten. **Red on the old
behaviour, measured rather than assumed:** with `fallback_status` forced to
return `nil` and nothing else changed, **7 of those 8 fail** — the eighth is the
negative case ("adds nothing when a rule already leaves the entry node") and
correctly stays green. Eleven pre-existing examples also moved from `edges` to
`stored_edges` where what they assert is which *population* was read; that is
what they were about, and the fallback now has assertions of its own rather than
being filtered out silently.

### F02 — With a mixed scope the issue panel says "no change of status is permitted" while the status list offers six

- **Status:** fixed
- **Severity:** major
- **Confidence:** confirmed
- **Category:** ux
- **Where:** `app/views/project_workflow_maps/_map.html.erb:93`,
  `config/locales/en.yml:113` (and the same key in the other seven files)
- **Invariant touched:** INV-3 (in its user-visible half — the three states must
  stay distinguishable *to the reader*, not only in the database)

**What is wrong**

The WP8 panel renders `text_project_workflow_map_own_empty` whenever **any** of
the reader's roles is in the `own_empty` state:

```erb
<% if @map.role_states.any? { |role_state| role_state.state == :own_empty } %>
```

The string is absolute — *"This project has its own workflow for this tracker and
role, and it holds no rule at all, so no change of status is permitted."* — so a
reader who holds two roles, one overridden-and-empty and one with rules, is told
that nothing is permitted while the form beside the sentence offers a full status
list.

This is not WP9's defect; it predates it. But WP9 met exactly this case on the new
screen and solved it in words — `text_project_workflow_graph_empty` opens with
*"At least one of the selected roles…"* and closes with *"…for it"* — and the
correction was not carried back to the panel. The two screens now describe the
same situation, one correctly and one not.

**Why it matters**

The panel's whole job is to explain the status list, and it says so itself two
lines further down (*"the status list on the form stays the authority"*). A reader
debugging *why can I not change this status* is handed a sentence that contradicts
what they can see, on the one screen built to stop that from happening. Multiple
roles per member is ordinary in Redmine, and per-role scopes are the plugin's
central idea, so the combination is not exotic.

**How I verified it**

On the live host: gave project *Pilot* an own workflow for Manager (31 rules) and
an own **empty** workflow for Developer, and logged in as a user holding both.

```
statuskeuzelijst op issue #2: 6 -> New, In Progress, Resolved,
                                   Wacht op antwoord van de klant, Closed, Rejected
paneel zegt: This project has its own workflow for this tracker and role, and it
             holds no rule at all, so no change of status is permitted. ...
```

The graph screen for the same project and roles says it correctly in the same
browser session.

**Suggested direction**

The panel already knows `uniform_state`. Either say the absolute sentence only
when the state is uniform and a per-role sentence otherwise, or adopt WP9's
wording for the non-uniform case. Whichever, the eight locale files move together
and the two screens should end up saying the same thing about the same state — a
spec asserting that a mixed scope does not produce the absolute sentence is the
regression test, and it is red on the current code.

**Resolution:**

Fixed on `claude/dev`. `app/views/project_workflow_maps/_map.html.erb` now
picks between the absolute sentence and a new
`text_project_workflow_map_own_empty_some` on `@map.uniform_state` — the same
question the diagram screen asks, answered the same way, so the two screens
agree. New key in all **eight** locale files (`en` and `nl` by hand, the other
six translated).

Two examples in `spec/controllers/project_workflow_maps_controller_spec.rb`, one
per direction: a reader holding two roles, one overridden-and-empty and one with
rules, must *not* see the absolute sentence; a reader whose every role is in that
state must still see it. **Red on the old view, confirmed by running the first
of the two against `git show HEAD:...` of that file:** *"expected … not to
include 'This project has its own workflow for this tracker and role, and it
holds no rule at all, so no change of status is permitted.'"*

### F03 — Longest-path layering turns Redmine's default workflow, which is a complete graph, into unreadable spaghetti

- **Status:** fixed
- **Severity:** major
- **Confidence:** confirmed
- **Category:** ux
- **Where:** `lib/redmine_project_workflows/services/workflow_graph_ranking.rb:128`
- **Invariant touched:** none

**What is wrong**

`assign_layers` places a node one layer to the right of the furthest of its
forward predecessors — the standard longest-path ranking. On a workflow where
every status may become every other, which is precisely what
`redmine:load_default_data` seeds, the cycle break leaves a Hamiltonian forward
chain and the longest path gives **one column per status**. Six statuses become
seven columns descending diagonally, and every edge that is not a chain edge
becomes a long arc sweeping the width of the canvas.

**Why it matters**

Measured on the default workflow with the entry rule added (so that F01 is not
what is being seen): a 1420 × 750 drawing with seven columns, five rows and 31
edges, in which the arcs cross each other so densely that no question can be
answered from it. `docs/implementation-plan.md`'s WP9 opens by naming Jira's
weakness as *"it schaalt slecht — bij twintig statussen wordt het spaghetti"*;
this reaches that state at **six**. The screen is honest and it is correct, and it
is not usable, which for a feature whose entire purpose is to be looked at is a
defect rather than a limitation.

**How I verified it**

Live, in Chromium, on the default workflow with one `old_status_id = 0` rule
added:

```
geometrie: {"viewBox":[0,0,1420,750],"outside":0,"overlaps":0,"band":0,
            "nodes":7,"edges":31,"rows":5,"cols":7}
```

Screenshot kept at `/tmp/pw/wp9/05-drawing.png` during the session. Nothing is
clipped and nothing overlaps — the layout is doing exactly what it says; it is the
ranking choice that produces the shape.

**Suggested direction**

Two directions, and they are not exclusive. **Rank by shortest path from the entry
node rather than longest.** A complete graph then collapses to three layers —
entry, the default status, everything else — which is both readable and a truer
statement about the workflow ("from New you may go anywhere in one step"), where
the longest path asserts a seven-stage progression that does not exist. Longest
path is the right default for a sparse, genuinely staged workflow; it is the wrong
one for a dense one, so the choice may have to depend on the density. **And say it
in words when the graph is near-complete:** a workflow in which every status
reaches every other has no shape to draw, and a sentence saying so is more useful
than any picture of it. That is the same instinct the diagnostics section already
has, applied one level up.

Whichever way, the change belongs in `WorkflowGraphRanking` alone — the layout,
the routing and the extent all stay as they are — and a spec pinning the layer
count for a complete graph on five statuses is the gate.

**Resolution:**

Fixed on `claude/dev`, and **not by the first of the two suggested directions**
— that one was investigated and rejected, which is worth recording because it is
the more obvious of the two.

*Ranking by shortest path does not work here.* BFS layering only guarantees
`layer(v) ≤ layer(u) + 1` for an edge `u → v`, so a forward edge can land inside
a layer or point leftwards, and a layered drawing has nowhere to put either —
`chain_for`, the routing and the straightening all assume every forward edge
spans at least one layer to the right. It also would not remove the arcs: a
complete graph over five statuses collapsed into three layers still has twenty
edges *between the members of one layer*. The claim in the finding that "the
change belongs in `WorkflowGraphRanking` alone" does not hold.

So the second direction is the whole fix. `Result#dense?` judges it — at least
four statuses, at least nine tenths of the possible moves present, entry arrows
excluded, integer arithmetic throughout (a threshold that decides what a screen
renders must not be able to differ in its last digit between platforms) — and
`graph.html.erb` then says the workflow permits nearly every move and folds the
picture into a `<details>` with *Show the diagram anyway*. Folded, not deleted:
plain HTML, no JavaScript, and no stylesheet the plugin does not ship.

Four examples on the judgement in `workflow_graph_query_spec.rb` (complete over
four is dense; a staged chain is not; complete over three is not; the entry
arrow does not count) and two on the screen in `project_workflows_graph_spec.rb`.
**Red on the old view:** both screen examples fail against
`git show HEAD:app/views/project_workflows/graph.html.erb`.

**Class B, logged in `docs/DECISIONS.md`.** The two thresholds are a judgement
about readability rather than a fact, and each is one constant.

### F04 — The band of unreachable statuses is one flat row with no ordering of its own

- **Status:** fixed
- **Severity:** minor
- **Confidence:** confirmed
- **Category:** ux
- **Where:** `lib/redmine_project_workflows/services/workflow_graph_layout.rb:223`
- **Invariant touched:** none

**What is wrong**

Statuses the entry node cannot reach are placed side by side in a single row below
the drawing, in query order, and the edges among them are all routed as returning
bows beneath that row. The band gets none of the three ranking phases the main
graph gets: no layering, no ordering, no straightening.

**Why it matters**

Where the band holds one or two statuses — the case it was designed for — this is
right and reads well. Where it holds several that have edges among them, every one
of those edges becomes a bow under the same row, and they stack into a bundle of
near-identical arcs that cannot be told apart. Today that is mostly visible
*through* F01, which puts every status in the band at once; but it is reachable on
its own by any project whose workflow has a genuinely unreachable cluster, which
is exactly the case the band exists to make visible.

**How I verified it**

Visible in the same browser walk as F01 — six band nodes, thirty edges, all bowed
under one row (`/tmp/pw/wp9/02-graph-union.png`). Read `place_band` and
`band_top_for` to confirm the band takes no part in `WorkflowGraphRanking`.

**Suggested direction**

Run the band's own sub-graph through the same ranking the main graph gets, from
whichever of its nodes have no incoming edge inside the band. It is the same three
phases on a smaller input, so it costs a call rather than an algorithm. If that is
judged not worth it, the honest alternative is to cap the band — draw the first
few and say in words how many more there are — because a bundle of indistinct arcs
is a picture that claims to inform and does not. Worth doing after F01, since F01
is what makes the band large in the first place.

**Resolution:**

Fixed on `claude/dev`, by the finding's own first suggestion.
`WorkflowGraphRanking` now takes `roots:`, and `WorkflowGraphLayout` runs it a
second time over the band's own sub-graph with **every** band node a root — the
band is by definition what the entry node cannot reach, so it has no single
starting point, and taking them all is also what guarantees no second band can
appear inside the first. The band is then placed by the same `even_spacing` and
`straighten` passes as the main graph, offset below it, and an edge inside the
band routes as a forward arrow unless it closes a cycle there. `place_band` is
gone; `route` merges the two rankings' `back_keys` and `crossings`, which are
disjoint by construction because an edge is wholly inside the band or wholly
outside it.

Five examples in `spec/services/workflow_graph_layout_spec.rb`. **Red on the old
layout, confirmed by running them against `git show HEAD:...` of the layout and
the ranking: 3 of the 5 fail** — a chain in the band came back with three `nil`
layers on one row, and every edge inside the band came back with `back` true.
The other two are the guards that must *not* change (an edge returning inside the
band still bows; an edge leaving the band for the drawing above it still bows)
and correctly pass either way.

### F05 — Two adjacent action links on the settings tab read as one sentence, and the second is the least reversible action on the screen

- **Status:** fixed
- **Severity:** minor
- **Confidence:** confirmed
- **Category:** ux
- **Where:** `app/views/project_workflows/_scope_actions.html.erb:27-43` (the two pairs begin at lines 27/31 and 36/40)
- **Invariant touched:** INV-3 (its user-visible half again: the three actions
  must stay distinguishable to the person clicking them)

**What is wrong**

The partial renders two `link_to` calls with nothing but ERB whitespace between
them, so the browser shows them as one run of text:

> Give own workflow (copy of the generic one) Give own empty workflow

and, for a combination that is already overridden:

> Empty this workflow Return to the generic workflow

Redmine's own idiom for adjacent contextual actions is a `contextual` block or an
explicit separator; nothing else in this plugin puts two bare links side by side.

**Why it matters**

*Give own empty workflow* is the most consequential thing either screen offers —
it is the state in which no status change is permitted at all — and it currently
sits at the end of a phrase that begins with a different action, with no visual
break to say where one link ends and the next begins. Both are behind a
confirmation dialogue, so a mis-click is recoverable; what is not recoverable is
the reading, and a reader scanning the row is being asked to find the seam
themselves.

**How I verified it**

Seen in Chromium on the live settings tab during the browser walk of 2026-08-28
(the screenshot from that session showed the row reading as one sentence), and
confirmed in the source: the *give* pair is the `link_to` at line 36 followed by
the one at line 40, and the *undo* pair the ones at lines 27 and 31, with nothing
but ERB newline whitespace between each pair.

**Filed late, and that is worth recording.** This was found during the browser
session of 2026-08-28, reported to Jan in conversation, and never written to a
findings file — so the fixing session that followed had no way to see it. It is
recorded here so that it stops depending on somebody remembering. Nothing about
the finding changed in the meantime; the file is untouched since `6571ad9`.

**Suggested direction**

Whatever separator the rest of the plugin would use in a table cell. `docs/design.md`
should end up with one answer for adjacent actions rather than this being decided
per view.

**Resolution:**

Fixed on `claude/dev`. A pipe between each pair in
`app/views/project_workflows/_scope_actions.html.erb`, which is Redmine's own
idiom for adjacent links in running text —
`app/views/projects/show.html.erb` puts one between *Summary*, *Calendar* and
*Gantt*. Chosen over a `contextual` block (the wrong element inside a table cell)
and over a CSS separator (the plugin ships no stylesheet, and an inline style is
one a theme cannot reach). It fixes both pairs, the *undo* one included.

Two examples in `spec/controllers/project_workflows_controller_spec.rb`, matching
`</a>\s*\|\s*<a` inside the `project-workflow-scope-actions` span — scoped,
because the rest of a Redmine page is full of adjacent anchors. **Red on the old
view:** both fail against `git show HEAD:...` of the partial, with the span's
actual markup in the message.

`docs/design.md` does not yet carry a general rule for adjacent actions, which
the finding also asks for; the pipe is now what both call sites use, and that is
the answer worth writing down if a third one ever appears.
