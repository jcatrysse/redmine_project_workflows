## Summary

The plugin has a comprehensible architecture and addresses a real gap in
Redmine. The split into query and writer services is a good step towards
maintainability, writes are transactional, generic and project writes are
properly isolated from each other, and the foreign key prevents orphaned rules.

The central conclusion is that the data model cannot distinguish a project that
inherits the generic workflow from one with a deliberately empty workflow. The
existence of at least one project rule is used as proof that an override is
active, so removing the last rule silently returns the project to the generic
workflow. That is not a UX problem but a functional limit.

**Counts:** blocker 1 · major 4 · minor 4 · nit 0 · question 0
**Verified:** 10 of 11 stand; 1 adjusted.

### F01 — An empty project override cannot be represented

- **Status:** fixed
- **Severity:** blocker
- **Confidence:** confirmed
- **Category:** correctness
- **Where:** `lib/redmine_project_workflows/services/resolver.rb:12-21`, `services/transition_query.rb:31-48`, `services/transition_writer.rb:26-49`
- **Invariant touched:** INV-3, INV-5

**What is wrong**

`Resolver#overridden_role_ids_for` derives "this project overrides" from the
existence of rows. The writers only persist ticked cells, so setting every cell
to No leaves nothing behind, and the resolver stops seeing an override.

**Why it matters**

A project administrator who wants "no transitions at all for this role and
tracker here" cannot express it. Setting everything to No re-enables the
generic workflow instead — the opposite of the intent, with no warning.

**How I verified it**

A spec on Redmine 5.1 and again on 7.0: two generic transitions, add one
project rule, then remove it. The allowed statuses go from the generic pair to
the single project rule and back to the generic pair.
`spec/characterization/override_semantics_spec.rb`.

Verification also widened it: the same mechanism makes a *partial* override
impossible. Adding one project rule removes **all** generic transitions for
that tracker and role, which is the case users actually meet. The administration
UI masks it — selecting a project with no rules shows an empty matrix, so an
administrator fills in the complete set and gets a full override that works.

**Suggested direction**

An explicit scope record per (project, tracker, role, rule type), so that
inheriting, overriding and overriding-with-nothing are three states rather than
two.

**Resolution:** fixed in WP1, as suggested. `project_workflow_scopes` holds one
row per (project, tracker, role, rule type); its presence is the decision, its
absence is inheritance, and a scope with no rules is an own *empty* workflow.
`Resolver` reads that table and nothing else. The characterization file is gone;
its examples are inverted in `spec/models/override_semantics_spec.rb`, where
"allows no transition at all when the scope is left without rules" and "tells an
empty own workflow apart from inheritance" state the two cases this finding
said could not be expressed.

### F02 — Copying to the generic workflow only takes the wrong path

- **Status:** fixed
- **Severity:** major
- **Confidence:** confirmed
- **Category:** correctness
- **Where:** `lib/redmine_project_workflows/patches/workflows_controller_patch.rb:118-120, 171-173, 175-190`

**What is wrong**

`duplicate` uses the project-aware copy path only when `project_context?` is
true, and that reads `@projects_for_update`, which `load_project_options` fills
after stripping `global`. Selecting only the generic workflow as the target
therefore leaves the list empty and the action falls through to core's `super`.

**Why it matters**

Core then copies generic to generic and ignores the chosen source project
entirely. No error — just the wrong data. "Generic plus a real project"
happens to reach the correct path, which makes the failure look intermittent.

**How I verified it**

A controller spec: one rule in the source project, copy to `global` only, zero
rows arrive. `spec/characterization/known_issues_spec.rb`.

**Suggested direction**

Decide the custom path on the presence of plugin parameters, not on a non-empty
project list.

**Resolution:** fixed in WP0, as suggested. `project_context?` is now
`PROJECT_PARAM_KEYS.any? { |key| Array.wrap(params[key]).any?(&:present?) }`
over `project_id`, `target_project_ids` and `source_project_id`. Selecting only
the generic workflow reaches the plugin's `duplicate`, which resolves `global`
to `project_id = nil` and honours the chosen source project. The
characterization example was inverted into "copies from the source project when
the generic workflow is the only target" in
`spec/controllers/workflows_controller_spec.rb`; it fails on the old code.

The same change makes `edit`, `update`, `permissions` and `update_permissions`
take the plugin's path for an explicit `project_id=global`, which writes the
same rows as core's path did (core's writers are routed through the plugin's)
but redirects back to the selection instead of to the referer.

### F03 — Copy target project ids are not validated

- **Status:** fixed
- **Severity:** major
- **Confidence:** confirmed
- **Category:** correctness
- **Where:** `lib/redmine_project_workflows/patches/workflows_controller_patch.rb:112-121, 191-199`

**What is wrong**

The source project value is checked for shape and existence; target values are
only checked for being non-blank.

**Why it matters**

The reviewer expected `Integer(...)` to raise or a foreign key to fail.
Verification found a different and earlier route: `load_project_options` does
check existence and calls `render_404`, but `render_404` renders and returns
`false` — it does not abort the action. `duplicate` continues and renders a
second time.

**How I verified it**

`post :duplicate` with `target_project_ids: ['999999']` and again with
`['abc']`. Both raise `AbstractController::DoubleRenderError`, so the user gets
a 500 with a 404 page half sent. `spec/characterization/known_issues_spec.rb`.

**Suggested direction**

Two changes, not one: a strict whitelist (`global` or digits, loaded in one
query, de-duplicated, reported as a translated validation error), **and** a
`return if performed?` guard after every `load_project_options` call.

**Resolution:** fixed in WP0, both changes.

`load_project_options` no longer renders anything. It de-duplicates, checks
each value against `global` / `all` / digits, resolves the rest in one query,
and collects everything it rejected in `@invalid_project_ids`. Each caller then
decides and returns: `render_404` followed by `return if performed?` on the
matrix screens and on `copy`.

The copy form's target selector is a different control with a different set of
valid values — `global` or a project id, never `all` — so `duplicate` validates
it separately in `validated_target_project_ids` and reports a rejected value as
`error_workflow_copy_target_project`, a new key present in all eight locale
files. Both characterization examples were inverted in
`spec/controllers/workflows_controller_spec.rb`, together with `all` as a
target, "writes nothing when a target is invalid", and the de-duplication case
that used to 404 for the same project id given twice. All fail on the old
code.

### F04 — "Only used statuses" does not show the effective workflow

- **Status:** fixed
- **Severity:** major
- **Confidence:** confirmed
- **Category:** correctness, ux
- **Where:** `lib/redmine_project_workflows/patches/workflows_controller_patch.rb:252-268`

**What is wrong**

`find_statuses` filters on the physically selected `project_id` values with no
generic fallback, although `StatusListQuery` can already resolve that.

**Why it matters**

Verification sharpened the symptom: for a project with no rules of its own the
query returns nothing, and `.presence` then falls back to **every** status. The
filter silently switches itself off in exactly the case where it is wanted, and
becomes too narrow as soon as one project rule exists.

**How I verified it**

Two generic statuses in use; the filter renders 6 of 6 statuses.
`spec/characterization/known_issues_spec.rb`.

**Suggested direction**

Decide explicitly whether the filter means "physically configured" or
"effectively in use", and say so in the label. For administrators the second is
the useful one.

**Resolution:** fixed in WP2. `find_statuses` now asks
`StatusListQuery.status_ids_for_pairs` for the effective workflow of the
selection instead of reading the rows physically stored against it, so a project
that inherits shows the generic statuses. The `.presence` fallback to every
status stays, but it now fires only when the selection's workflow really is
empty — which is the one case where showing everything is right, because an
empty matrix cannot otherwise be filled in. Core's own role filter is kept.

The filter therefore means "effectively in use", as this finding recommended.
The **label** was not changed: it lives inline in core's two views as
`l(:label_display_used_statuses_only)`, so changing it would need two more
Deface anchors and a spec each (INV-9) to alter the text from "used by this
tracker" to something barely different, since with a project selected that
tracker's workflow *is* the project's effective one. Put to Jan and **answered
A on 2026-08-26**: core's wording stands. Recorded in `docs/DECISIONS.md`.

The pointer said WP1; that was wrong. `find_statuses` is a controller method,
not one of the four services WP1 rewrote.

### F05 — `insert_all` bypasses model validation

- **Status:** fixed
- **Severity:** major
- **Confidence:** confirmed
- **Category:** correctness, security
- **Where:** `lib/redmine_project_workflows/services/permission_writer.rb:44-75`, `patches/workflow_permission_patch.rb:6-14`
- **Invariant touched:** INV-2

**What is wrong**

The writers build rows from parameters and insert them with `insert_all`, which
runs no validations. Status ids, field names and rule names arrive unchecked.

**Why it matters**

Verification found this heavier than reported. Because `WorkflowPermissionPatch`
routes Redmine's *generic* write path through the plugin's writer as well,
`validates_inclusion_of :rule` and `validate_field_name` no longer run for
ordinary generic workflow updates either. The plugin removed a core protection
from installations that never use a project override.

**How I verified it**

`WorkflowPermission.create!` with `rule: 'bogus'` raises, as core intends;
`WorkflowPermission.replace_permissions` with the same value writes it. A field
named `niet_bestaand_veld` also lands. `spec/characterization/known_issues_spec.rb`.

**Suggested direction**

Whitelist server-side in both writers: `always`/`author`/`assignee`, only
`readonly`/`required`/empty, only status ids from the permitted matrix, only
known core and custom field names. Keep `insert_all`.

**Resolution:** fixed in WP0, as suggested, and `insert_all` is kept.

`PermissionWriter.sanitize_permissions` accepts a rule only if it is blank or
one of `readonly` / `required`, a field name only if it is in
`Tracker::CORE_FIELDS_ALL` or the id of an existing `IssueCustomField` — core
accepts any run of digits, so this is narrower — and a status id only if the
`IssueStatus` exists. `TransitionWriter.sanitize_transitions` accepts only the
rule names `always` / `author` / `assignee`, only the cell values the matrix can
submit, a new status id that exists, and an old status id that exists or is `0`,
the pseudo status core uses for a new issue.

One deliberate difference from core: a rejected entry is dropped *before* the
delete as well as before the insert, so an unacceptable value changes nothing
rather than clearing the rule it names. Core destroys first and then fails to
create. This also repaired a defect neither review had found: a transitions
cell whose three rules were all left at "no change" arrived as an empty rule
hash, which still contributed to the delete and then inserted nothing — "leave
this as it is" removed the transition. There is a regression test for it.

Both characterization examples were inverted into a `server-side validation`
group in `spec/services/permission_writer_spec.rb`, with a matching group in
`spec/services/transition_writer_spec.rb`. Eleven of the new examples fail on
the old code.

### F06 — No unique constraints; concurrent writes can duplicate

- **Status:** adjusted
- **Severity:** minor
- **Confidence:** probable
- **Category:** concurrency
- **Where:** `db/migrate/002_add_workflow_composite_indexes.rb`

**What is wrong**

The added composite indexes are not unique. Delete-then-insert is transactional
per writer, but two administrators can delete the same scope concurrently and
then both insert.

**Why it matters**

Duplicate rows inflate the counts the matrix compares against
`workflow_permissions_matrix_size`, which is what decides whether a cell renders
as a checkbox or as a mixed dropdown.

**How I verified it**

Read-only. Core Redmine has no unique index on `workflows` either, so this is a
pre-existing gap the plugin widens rather than a regression. Uniqueness is also
not trivial to define while `author`/`assignee` produce two rows per transition.

**Suggested direction**

Settle the canonical key first, clean up existing duplicates, then add the
index. After the scope model, not before.

**Resolution:** the scope-table half was fixed in WP1: migration 004 ships a
unique index on (project, tracker, role, rule type), and
`spec/models/project_workflow_scope_spec.rb` asserts that a duplicate is refused
at the database level, not only by the validation.

The `workflows` half was worked in WP2 and **the suggested direction turned out
not to be available.** A unique index there would have to include `project_id`
and `field_name`, and both are nullable — NULL project id is what "generic"
means, NULL field name is what "transition" means. PostgreSQL, MySQL and MariaDB
all treat NULLs in a unique index as *distinct*, so the index would constrain
nothing for the generic rows, which are the majority. PostgreSQL 15 could say
`NULLS NOT DISTINCT` and MySQL 8 could index an expression; MariaDB can do
neither, and Redmine 5.1 has to run on older PostgreSQL. Making `project_id` NOT
NULL with 0 for generic would fix it and contradicts `docs/design.md`; that was
put to Jan as an ADR conversation and **answered A on 2026-08-26** — no unique
constraint, keep `project_id` nullable, repair with the rake task. Recorded in
`docs/DECISIONS.md`.

What WP2 did instead, covering the same ground from the other side:

- `spec/services/workflow_idempotency_spec.rb` holds both writers to "saving the
  same matrix twice is the same as saving it once", generic and project, and
  pins that a repeat save does not restamp the scope either. The writers cannot
  produce a duplicate within one call.
- `rake redmine_project_workflows:deduplicate_workflow_rules` repairs a database
  that already has duplicates. Exact duplicates only: two field permissions that
  agree on everything but the rule are a contradiction for an administrator to
  settle, not a duplicate to delete. The two populations are swept separately, so
  the generic pass cannot touch a project row (INV-1).
- Migration 005 drops the two of the four indexes on `workflows` that could
  never be chosen over the others — same columns in a different order, and a
  strict prefix — because every index is paid for on every insert and a workflow
  save inserts a whole matrix.

The residual race — two administrators saving the same matrix at the same
moment — is still open, and is core's as much as the plugin's.
`docs/design.md` records all of this.

### F07 — The hot-path override check is system-wide and badly indexed

- **Status:** fixed
- **Severity:** minor
- **Confidence:** confirmed
- **Category:** performance
- **Where:** `services/transition_query.rb:10-17`, `services/permission_query.rb:9-16`, `db/migrate/002`

**What is wrong**

`override_active?` asks whether *any* project has an override for this tracker
and role, not whether the current project has one. All the composite indexes
lead with `project_id`, while the query uses `tracker_id`, `role_id` and
`project_id IS NOT NULL`.

**Why it matters**

Once one project override exists anywhere, every issue edit for that tracker
and role takes the slower plugin path, including in projects that never had an
override.

**How I verified it**

Read-only.

**Suggested direction**

With an explicit scope table this becomes a point lookup on the current
project, with an index ordered for it.

**Resolution:** fixed in WP1, as suggested. `override_active?` no longer exists.
`Resolver.scoped_role_ids` reads the leading columns of
`index_project_workflow_scopes_unique` (project, tracker, rule type) and is
cached per request in `RedmineProjectWorkflows::Current`, so a list of issues in
one project and tracker costs one query rather than one per issue.

The finding's premise about the *other* path turned out to be worse than
described, and WP1 had to deal with it: falling back to core for a project
without an override is not merely slower, it is wrong. Core's queries carry no
`project_id` predicate, so an inheriting project would have read every other
project's rules (INV-4). The plugin now answers both methods itself.

### F08 — `rolled_up_statuses` handles project hierarchies incompletely

- **Status:** fixed
- **Severity:** major
- **Confidence:** confirmed
- **Category:** correctness
- **Where:** `lib/redmine_project_workflows/patches/project_patch.rb:6-15`

**What is wrong**

The patch collects roles from the project and its descendants but resolves the
workflow against `self`, so a subproject's own workflow can be missing from the
parent's rolled-up status list.

**Why it matters**

Verification found a heavier fault underneath. Core ignores roles entirely
here; the patch adds a role filter based on memberships. A project with no
members yields no roles, `StatusListQuery` returns nothing, and
`rolled_up_statuses` is empty — which empties the status filter in issue
queries and the status report, even where no override exists anywhere.

**How I verified it**

A member-less project with one tracker and one generic transition returns `[]`
where core's own query finds the transition.
`spec/characterization/known_issues_spec.rb`.

**Suggested direction**

Drop the role filter, matching core, and compute effective statuses per project
across the tree, then union. Add tests for parent-only, child-only and
differing overrides.

**Resolution:** fixed in WP2, both halves. The role filter is gone: a project
without members now answers with the generic used statuses, as core does. And
the tree is resolved per project rather than against `self` — `StatusListQuery`
took a `pairs` API for the purpose, so each (project, tracker) pair is resolved
against its own scope (INV-6) and the results unioned, in two queries however
large the tree. `spec/models/project_statuses_spec.rb` covers parent-only,
child-only, mixed, the member-less project, a role nobody holds, and an archived
subproject; five of the six fail if only the old decision code is put back.

### F09 — Thread-local cache fallback can go stale

- **Status:** fixed
- **Severity:** minor
- **Confidence:** confirmed
- **Category:** correctness
- **Where:** `lib/redmine_project_workflows/patches/issue_patch.rb:107-116`

**What is wrong**

Custom field visibility is cached in `RequestStore` when available and in
`Thread.current` otherwise. A threaded application server reuses a thread across
requests, so the fallback outlives the request.

**Why it matters**

Configuration changes would not be seen until the thread is recycled.

**How I verified it**

Read-only. Redmine bundles `request_store` itself, so the fallback branch is
dead code in any normal installation — which is an argument for removing it,
not for keeping it.

**Suggested direction**

Use only the request-scoped cache, or none.

**Resolution:** fixed in WP0, but not as described: the premise is wrong on one
supported version. **Redmine 7.0 no longer bundles `request_store` at all** —
it is absent from its `Gemfile`, and `defined?(::RequestStore)` is false in a
booted 7.0. On 7.0 the `Thread.current` branch was therefore not dead code but
the only path the cache ever took, which makes the finding more serious than
reported there and inapplicable as stated. Removing the fallback and keeping
`RequestStore` would have left 7.0 with no cache at all, and one query per issue
where an issue list renders many.

The cache moved to `RedmineProjectWorkflows::Current`, an
`ActiveSupport::CurrentAttributes` subclass. Rails resets it around every
request and every job through the executor on all three supported versions, so
it is genuinely request-scoped, and `Thread.current` is gone from `lib/`.
`spec/plugin_conventions_spec.rb` asserts that the map survives within one
request and not past a reset; it fails on the old code, where the second call
recomputed because 7.0 has no `RequestStore` to memoise into.

### F10 — Deface selectors are fragile across Redmine upgrades

- **Status:** adjusted
- **Severity:** minor
- **Confidence:** confirmed as a risk, not as a current defect
- **Category:** dependency, build
- **Where:** `lib/redmine_project_workflows/overrides/*.rb`

**What is wrong**

The overrides match exact ERB fragments. A small upstream template change makes
an override stop applying with no compile error.

**Why it matters**

The plugin's project selector would silently disappear, and the pages would
look like stock Redmine while the controller still expects the parameters.

**How I verified it**

All five anchors exist verbatim in 5.1, 6.1 and 7.0, and `workflows/edit`,
`permissions` and `copy` are byte-identical between 6.1 and 7.0. All five
overrides were confirmed to reach the rendered page on a running Redmine 7.0.0
under Rails 8.1.

**Suggested direction**

The recommendation stands as a control, not as a repair: assert per supported
version that each override actually applies.

**Resolution:** implemented as `spec/integration/deface_overrides_spec.rb`,
which asserts each override against the real rendered page and runs on every
version in the CI matrix. Severity reduced from "compatibility risk" to a
covered control. The underlying dependency risk — Deface 1.9.0 has had no
release since 2022 and upstream tests only to Rails 8.0 — is recorded in
`docs/design.md` rather than as an open finding.

### F11 — The README understates the operational risks

- **Status:** open
- **Severity:** minor
- **Confidence:** confirmed
- **Category:** docs
- **Where:** `README.md`

**What is wrong**

The README calls the plugin alpha but does not say that a project override
replaces the generic workflow for a whole tracker and role scope, that an empty
override is currently impossible, what "generic" means, or what happens when
several projects are selected.

**Why it matters**

Everything the plugin does that is surprising is undocumented, and the
surprising parts are the ones that lose configuration.

**How I verified it**

Read the README. Verification added one factual error to the list: it said
Redmine 6.0 and 6.1 "should also work", and on those versions the project
selector raises a JavaScript error (see `2026-08-25-claude.md` F04).

**Suggested direction**

Document the three states, the replacing semantics and the meaning of
"generic"; keep compatibility claims to what CI demonstrates.

**Resolution:** _(open — WP7; the compatibility claim itself was corrected in commit 200c824)_
