Executive Summary

    Production readiness: NOT READY

    Security risk: MEDIUM

    Code quality: GOOD

    Maintainability: FAIR

    Redmine integration quality: FAIR

    Test confidence: MEDIUM

The plugin implements project-specific Redmine workflows by adding a nullable project_id to Redmine’s core workflows table and introducing a separate scope table that distinguishes inheritance, an owned workflow, and an intentionally empty workflow. Generic rules and project-specific rules are resolved per project, tracker, role, and rule type. The design is coherent and substantially better documented and tested than most early-stage plugins. The separation of scope decisions from workflow rules is especially important and correct.

Nevertheless, I would not approve it for production today:

    The repository itself explicitly identifies the plugin as alpha and says not to use it in production.

    It replaces or materially modifies a large amount of Redmine core workflow behavior. Core-method drift is checked only for three selected Redmine minor versions, while an unrecognized future or intermediate minor is allowed to boot and its drift test is skipped. This creates meaningful upgrade and authorization risk.

    Concurrent generic-workflow saves can still create duplicate workflow rows. The database has no uniqueness constraint, the generic save path has no scope row it can lock, and the repository explicitly documents the resulting corruption of matrix presentation.

    The implementation relies on fifteen Deface overrides plus numerous prepended replacements of Redmine core methods. That is a large compatibility surface for a plugin whose registration declares only a minimum Redmine version.

    Deployment coverage is strong but narrower than Redmine’s general ecosystem: only Redmine 5.1, 6.1, and 7.0, Ruby 3.2/3.3, and PostgreSQL/MySQL/MariaDB are claimed.

I did not find a confirmed Critical authorization bypass, SQL injection, XSS, CSRF bypass, arbitrary code execution, unsafe deserialization, secret disclosure, or cross-project workflow write through the plugin’s controllers. Project-level writes consistently resolve the project from the path and run Redmine authorization before resolving tracker and role parameters.

No files were modified, as requested. Consequently, there was no commit and no pull request.
1. Plugin Architecture and Intended Behavior
Problem solved

The plugin extends Redmine’s global workflow model so that individual projects may replace the generic workflow for a particular:

    project;

    tracker;

    role;

    rule type:

        status transitions; or

        field permissions.

A project-specific workflow replaces rather than augments the generic workflow. Roles are resolved independently, and users holding multiple roles receive the union of what those roles permit.
Data model
Core-table extension

Migration 001 adds workflows.project_id, allowing a workflow rule to be either:

    generic: project_id IS NULL; or

    project-specific: project_id = <project id>.

It also introduces project-leading composite indexes.

A foreign key from workflows.project_id to projects.id is later added with cascading deletion.
Scope-decision table

project_workflow_scopes records the decision that a project owns a workflow for a tracker, role, and rule type. This is separate from rule existence so that these states remain distinguishable:

    no scope: inherit generic workflow;

    scope with rules: owned workflow;

    scope without rules: intentionally empty workflow.

The table has database foreign keys, NOT NULL columns, and a composite unique index.

This is the correct central data-model decision.
Main execution flows
Issue workflow evaluation

Issue is prepended with plugin behavior, and workflow queries split a user’s roles between:

    project-owned populations; and

    generic populations.

Every generated workflow relation explicitly includes a project_id predicate.
Project-level management

Routes under /projects/:project_id/workflow/... expose:

    transitions;

    permissions;

    comparison;

    graph;

    enable/own;

    inherit;

    clear.

The controller loads the project from the path, invokes Redmine’s authorize, and resolves tracker and role selections against server-built project option lists.
Administration management

The plugin extends Redmine’s core administration workflow matrices and adds bulk project selection. These paths remain administrator-only. Separate administrator-only scope actions support bulk enable, inherit, and clear operations.
Issue-form workflow map

A saved issue is loaded through Issue.visible, while a new-issue map requires add_issues on the project. The saved-issue route derives its project from the issue rather than trusting a project request parameter.
Project copy

The plugin uses Redmine’s project-copy hooks:

    a view hook adds the copy checkbox;

    a model hook copies scopes and their effective rules inside the surrounding project-copy transaction.

Failures are deliberately allowed to abort the whole copy.
Frontend

The main custom JavaScript supports bulk matrix row/column updates, confirmation thresholds, counters, and undo. It is exercised by a standalone Node test harness and has progressive HTML behavior around the workflow map.
External services and background jobs

I found:

    no background jobs;

    no outbound HTTP clients;

    no webhooks;

    no external API integrations;

    no runtime downloads;

    no file uploads;

    no shell execution from application code;

    no secrets handled by the plugin.

The only runtime gem dependency is Deface.
2. Findings
HIGH
ID: COMPAT-001

Severity: High
Confidence: Confirmed

Location:

    init.rb, plugin registration, lines 9–22.

    spec/upstream/core_drift_spec.rb, drift handling, lines 51–68.

    README.md, compatibility statement, lines 509–516.

    lib/redmine_project_workflows/services/core_method_digest.rb, architectural rationale, lines 8–25.

Problem

The plugin declares only a Redmine minimum version even though it reimplements numerous core workflow methods and only validates exact behavior on Redmine 5.1, 6.1, and 7.0. An unknown Redmine minor or future version is allowed to start, and the core-drift test explicitly skips rather than fails for an unrecognized version.

Evidence

requires_redmine version_or_higher: '5.1' permits every later Redmine release to load.

The compatibility documentation claims only Redmine 5.1, 6.1, and 7.0.

The drift spec skips if the running minor is absent from its digest table.

The repository itself acknowledges that semantic changes in Issue#new_statuses_allowed_to have previously changed which roles participate in workflow resolution and that an outdated copy could widen permissions.

Impact

An administrator can upgrade Redmine to an unverified minor or major version and receive a clean application boot while the plugin silently retains outdated behavior. Because the affected methods participate in issue transition and field-permission decisions, incompatibility can cause:

    status changes to be incorrectly permitted or denied;

    read-only or required fields to be enforced incorrectly;

    administration screens to overwrite or misread workflow rules;

    project-specific rules to leak into generic decisions;

    runtime failures in ordinary issue editing.

This is a release and upgrade blocker, even if the currently tested versions behave correctly.

Scenario

A site installs the plugin on Redmine 7.0 and later upgrades to 7.1. Redmine changes the role-resolution or safe-attributes logic. The plugin still boots because 7.1 is above 5.1. CI’s drift test would skip on 7.1 until a digest entry is added, so production may run an obsolete copied implementation.

Recommended fix

Use a two-layer compatibility policy:

    Keep the boot-safe minimum requirement if an upper-bound boot failure is considered operationally unacceptable.

    Add a runtime compatibility guard that:

        recognizes exact verified Redmine minor versions;

        emits a prominent administrator-visible warning and application log warning on unverified versions;

        optionally disables project workflow writes until compatibility is explicitly acknowledged.

    Change CI so an unknown version fails the compatibility job. A local developer may opt into an explicit “compatibility investigation” mode, but normal release CI should not skip.

    Document an exact upgrade procedure requiring:

        core drift review;

        oracle tests;

        Deface anchor verification;

        migrations;

        full database matrix execution.

    Reduce copied core methods where a stable hook or a narrowly scoped query extension can safely replace them.

Regression test

Add a plugin boot/integration test using a stubbed unsupported minor version and assert that:

    the warning is logged;

    the administration UI exposes the unsupported-version state;

    writes are blocked or require explicit administrative acknowledgment;

    reads do not crash;

    CI fails when the digest table lacks the tested minor.

MEDIUM
ID: DATA-001

Severity: Medium
Confidence: Confirmed

Location:

    README.md, maintenance section, lines 465–481.

    lib/redmine_project_workflows/services/matrix_scope.rb, generic/project locking distinction, lines 29–50.

    lib/redmine_project_workflows/services/transition_writer.rb, transaction and write sequence, lines 45–63.

    lib/redmine_project_workflows/services/permission_writer.rb, transaction and write sequence, lines 25–44.

Problem

The workflows table has no database uniqueness constraint, and concurrent generic workflow writes have no scope row to lock. Two administrators saving overlapping generic workflow matrices can produce duplicate rows or lost/interleaved results.

Project-specific writes are better protected because they lock their corresponding project_workflow_scopes rows. Generic writes explicitly return all pairs without taking an equivalent serialization lock.

Evidence

The README explicitly states that simultaneous saves can leave duplicate rows and that duplicate rows alter matrix rendering.

Both writers use delete-then-insert sequences within database transactions.

A database transaction makes each save atomic by itself, but it does not serialize two transactions targeting the same generic tracker/role cells.

Impact

Concurrent saves may cause:

    duplicate transition or permission rows;

    a normal checkbox to render as a mixed-value selector;

    inconsistent counts;

    one administrator’s changes to be overwritten or combined with another’s;

    misleading audit output;

    cleanup requiring a manual rake task.

The duplicate repair task does not resolve contradictory permission rows and cannot reconstruct which administrator’s write should have won.

Scenario

Two administrators open the same generic workflow matrix. Administrator A enables a transition while administrator B edits a related condition. Their delete/insert phases interleave. The final database contains duplicate or semantically conflicting rows even though both requests report success.

Recommended fix

Introduce an explicit serialization mechanism for generic workflow writes. Practical options include:

    a small plugin-owned lock table keyed by rule type, tracker, and role;

    PostgreSQL advisory locks only if equivalent MySQL/MariaDB semantics are implemented;

    pessimistic locks on a stable plugin-owned “generic scope lock” record;

    optimistic concurrency with a workflow revision token presented by the form, rejecting stale saves.

A generic lock table is likely the simplest cross-database approach. Acquire locks in deterministic key order before any delete or insert.

Keep the deduplication task as repair tooling, not as the primary integrity control.

Regression test

Add a real two-connection concurrency test for both writers:

    start two transactions targeting the same generic tracker/role;

    pause one after its delete;

    run the second save;

    release both;

    assert:

        no duplicate logical keys;

        deterministic final state;

        stale or losing save receives an explicit result;

        transition flags and permission rules remain internally consistent.

Run this on PostgreSQL, MySQL, and MariaDB.
ID: DEP-001

Severity: Medium
Confidence: High

Location:

    Gemfile, Deface dependency, lines 1–22.

    init.rb, hard runtime load, lines 57–60.

    .github/workflows/specs.yml, action versioning and permissions, lines 12–33.

Problem

The plugin’s sole runtime dependency, Deface, is unconstrained. A new installation resolves whatever current Deface release satisfies the host bundle, while failure to load Deface prevents the Redmine application from booting.

Evidence

The plugin declares gem 'deface' without a lower bound, upper bound, or known-good range.

init.rb catches LoadError only to raise another LoadError, making Deface absence or load failure fatal to plugin initialization and potentially to Redmine boot.

The comments argue that the host lockfile owns the resolved version. That protects repeat deployments using an existing lockfile, but it does not protect a new install or a future bundle update.

Impact

A future incompatible Deface release can:

    break Redmine boot;

    silently stop overrides from matching;

    produce malformed administration forms;

    conflict with another plugin’s dependency constraints.

This is not currently demonstrated as an exploitable supply-chain vulnerability, but it is a production deployment and repeatability risk.

Scenario

An administrator installs the plugin six months later or runs a broad bundle update. Bundler resolves a newer Deface version with changed Rails compatibility. The plugin then either aborts Redmine initialization or loads while some overrides no longer apply.

Recommended fix

Declare an evidence-based compatibility constraint, for example:

    a minimum known-good Deface version; and

    an upper bound on the next incompatible major version.

Do not pin to an exact patch unless necessary. Add a dependency-update job that periodically tests the newest allowed Deface version against all supported Redmine lines.

Document that production deployment must use and preserve the host application’s reviewed Gemfile.lock.

Regression test

Add CI cells for:

    the minimum supported Deface version;

    the latest allowed version.

Assert that every expected override is registered and matches exactly once.
ID: PERF-001

Severity: Medium
Confidence: Confirmed

Location:

    app/controllers/project_workflow_scopes_controller.rb, bulk “all projects” resolution, lines 56–69.

    app/controllers/project_workflow_inventories_controller.rb, filter option loading, lines 40–48.

    README.md, bulk-selection behavior, lines 162 onward.

Problem

Some administration paths materialize every project, tracker, and role into Ruby arrays or construct whole-installation write selections without pagination or a server-side upper bound.

The inventory loads all projects, trackers, and relevant roles before applying filters.

The bulk scope controller maps the all keyword to Project.pluck(:id).

Impact

For installations with thousands or tens of thousands of projects, an administrator can trigger:

    large Ruby allocations;

    very large IN predicates;

    long-running transactions;

    contention across many scope and workflow rows;

    request timeouts after the database has already performed substantial work;

    application-worker exhaustion.

This is administrator-only and therefore not an anonymous denial-of-service vulnerability, but administrators make mistakes and compromised admin accounts are within the threat model.

Scenario

An administrator selects all projects, multiple trackers, and multiple roles, then chooses “give own workflow.” The request copies a very large generic workflow population in one synchronous HTTP transaction. A proxy times out, the user retries, and the database remains heavily contended.

Recommended fix

For whole-installation writes:

    calculate the projected combination and rule count before executing;

    require a dedicated confirmation page;

    impose a configurable synchronous limit;

    process larger operations through a resumable, idempotent background job if the supported Redmine versions provide a reliable job backend;

    show progress and a durable operation result;

    lock and batch in deterministic order;

    make retries idempotent.

For the inventory:

    query filter options using relations and only materialize the current page where practical;

    consider searchable project selection for very large installations;

    measure memory and SQL time with a 10,000-project fixture.

Regression test

Add a scale-oriented test with at least:

    10,000 projects;

    several trackers and workflow roles;

    thousands of scope rows.

Assert query count, maximum materialized row count, and that an oversized synchronous write is refused or queued before data changes begin.

ID: BUG-001

Severity: Low
Confidence: Confirmed

Location:

    app/controllers/project_workflows_controller.rb, find_tracker_and_roles, lines 241–255.

    app/controllers/project_workflows_controller.rb, selected_roles, lines 257–285.

Problem

The graph role-selection code does not reject a request containing both a valid role ID and an invalid role ID, despite comments stating that any named role the project does not offer should produce a 404.

selected_roles intersects requested IDs with visible roles. find_tracker_and_roles returns 404 only when the resulting selection is empty. Therefore:

    role_id[]=valid&role_id[]=invalid silently renders the valid role;

    role_id[]=invalid returns 404.

Evidence

The stated contract says a role the project does not offer answers 404 rather than silently narrowing the selection.

The implementation checks only @roles.empty? && @visible_roles.any?.

The selection itself is an intersection and does not report rejected values.

Impact

This does not expose unauthorized workflow information because the invalid value is dropped. The practical impact is inconsistent request handling:

    malformed saved links appear to work while showing less than requested;

    API-like consumers cannot distinguish complete from partial resolution;

    logs and screenshots may claim a selection that was not actually rendered;

    the implementation contradicts its documented invariant.

Scenario

A link generated before a role deletion contains two role IDs. One role remains, and the other no longer exists. Instead of reporting a stale link, the graph silently renders only the surviving role.

Recommended fix

Resolve and validate all requested role IDs:

requested = requested_role_ids.uniq
selected = @visible_roles.select { |role| requested.include?(role.id.to_s) }
render_404 unless requested.empty? || selected.size == requested.size

Also reject duplicate or malformed nested values consistently.

Regression test

Add controller specs covering:

    one valid role;

    one invalid role;

    valid plus invalid;

    duplicate valid IDs;

    scalar role ID;

    nested/hash input;

    deleted role from a stale URL.

ID: MAINT-001

Severity: Low
Confidence: Confirmed

Location:

    lib/redmine_project_workflows.rb, patch installation, lines 63–84.

    docs/design.md, override count, line 465.

    spec/upstream/core_drift_spec.rb, copied methods discussion, lines 5–38.

Problem

The plugin has an unusually broad Redmine-core modification surface: multiple model/controller/helper prepends, direct singleton-class patches, helper-chain injection, and fifteen Deface overrides.

Evidence

Patch installation affects Issue, WorkflowsController, both workflow STI classes, WorkflowRule, WorkflowsHelper, Project, Role, Tracker, ProjectsController helpers, and IssuesController helpers.

The design documentation records fifteen Deface overrides.

The drift spec states that many core methods are reimplemented rather than delegated.

Impact

Even though the current code contains unusually strong drift and override tests, this surface increases:

    Redmine upgrade effort;

    conflict probability with other workflow plugins;

    load-order sensitivity;

    development reload risk;

    the chance that a UI anchor still matches syntactically but no longer has the intended semantics.

Scenario

Another plugin prepends Issue#new_statuses_allowed_to or replaces the workflows edit partial. Both plugins load, but load order determines which behavior wins or whether a Deface anchor sees the structure it expects.

Recommended fix

Do not perform a broad rewrite solely for style. Instead:

    Inventory every patched method and classify it as:

        unavoidable;

        replaceable by a Redmine hook;

        replaceable by one common query abstraction;

        UI-only and suitable for an owned plugin page.

    Prefer plugin-owned workflow administration pages over continuing to transform core views.

    Keep core patches minimal and delegate immediately into plugin services.

    Publish explicit incompatibility guidance for other workflow-altering plugins.

    Add a diagnostic page listing:

        patch ancestry;

        applied Deface overrides;

        unmatched or multiply matched overrides;

        Redmine version verification status.

Regression test

Add an integration test with a synthetic neighboring plugin that prepends the same key methods before and after this plugin. Verify either compatible composition or a clear startup/administrator diagnostic.

3. Architecture Assessment
Simplified architecture and data flow

Request / issue save
        |
        v
Redmine controller/model
        |
        +--> plugin controller authorization
        |       |
        |       +--> project from path / Issue.visible
        |       +--> tracker and role intersected with server-built options
        |
        +--> prepended Issue / Workflow APIs
                |
                v
        Resolver / WorkflowPopulations
                |
                +--> ProjectWorkflowScope:
                |      Does this project own this tracker/role/rule type?
                |
                +--> workflows.project_id = project.id
                |      for owned combinations
                |
                +--> workflows.project_id IS NULL
                       for inherited combinations

Write flow:

Authorized matrix request
        |
        v
Payload whitelist / normalization
        |
        v
Scope decision and lock
        |
        v
Delete only submitted cells
        |
        v
Bulk insert replacement rows
        |
        v
Touch audit columns + reset resolver cache + write safe audit log

Well-designed components
Explicit scope decision model

Separating ownership from rule existence is the strongest design choice. It prevents an empty owned workflow from being confused with inheritance. The database unique index and foreign keys reinforce the application model.
Project isolation discipline

The plugin consistently treats project_id as part of workflow query identity. WorkflowPopulations centralizes the split between owned and generic rows and always builds relations with an explicit project predicate.
Authorization design

Project-specific writes are protected by Redmine project permissions and membership requirements.

The controller performs authorization before resolving tracker and role choices, and those choices are intersected with project-derived lists.

The issue map correctly uses Issue.visible for saved issues and add_issues for new issues.
Input validation

Transition and permission payloads are narrowed through server-built status, rule, and field lists before delete/insert operations. Invalid leaves are dropped before deletion, preventing malformed inputs from clearing existing rules.
Migration integrity

The scope table includes:

    foreign keys;

    null constraints;

    composite uniqueness;

    supporting indexes;

    a set-based backfill.

The uninstall behavior is destructive but explicitly documented rather than hidden.
Operational logging

Workflow writes log IDs and counts rather than request bodies, issue content, or names. Unknown field types are represented by their class rather than their value.
Fragile components
Core method replacement

The central functionality necessarily changes Redmine’s workflow queries, but copying core method bodies creates a continuing semantic synchronization obligation. The digest/oracle suite mitigates this only for known versions.
Deface override volume

Fifteen overrides are a large frontend compatibility surface. Tests proving an anchor matches are valuable but cannot always prove that the surrounding core semantics remain appropriate.
Core schema modification

Adding a column, indexes, and a foreign key to workflows is more invasive than using a plugin-owned rule table. It enables reuse of Redmine workflow models but increases:

    upgrade coupling;

    migration duration and locking;

    uninstall complexity;

    conflict risk with other workflow plugins.

Synchronous whole-installation changes

Bulk workflow administration can span many projects and rules inside an HTTP request. This is operationally risky on large installations.
Unnecessarily complex areas

The graph subsystem contains several services for query, ranking, layout, text fitting, and extent calculation. This may be justified if the diagram remains a supported first-class feature, but it is a large maintenance commitment relative to the plugin’s central workflow-resolution purpose.

The greater concern is not individual service-object style; it is total feature breadth. The plugin simultaneously provides:

    core workflow replacement;

    project administration;

    global administration extensions;

    inventory;

    comparison;

    issue-form explanation;

    graph layout;

    bulk JavaScript with undo;

    project copying;

    role/tracker copy behavior;

    audit metadata.

For an alpha plugin, narrowing the production milestone to workflow resolution, administration, and permission correctness would reduce risk.
Redmine convention assessment

The plugin generally follows Redmine conventions:

    plugin registration and project module permissions;

    standard controllers and routes;

    Redmine authorization;

    hooks where real hooks exist;

    locale files;

    plugin migrations;

    administrator-only global administration.

The weaker area is the volume of monkey patching and Deface transformations. The code acknowledges and tests this, but tested fragility remains fragility.
Highest long-term maintenance risks

    Core workflow method replacements.

    Deface overrides of workflow administration screens.

    Direct extension of workflows.

    Concurrency behavior of generic workflow writes.

    Graph layout and browser/UI compatibility.

    Broad version floor combined with narrow exact-version verification.

4. Security Threat Model
Anonymous attacker

Realistic attempts:

    enumerate issue or project IDs through workflow-map routes;

    send malformed role/tracker/project parameters;

    force expensive pre-authorization queries;

    trigger reflected XSS through graph or filter inputs;

    perform CSRF writes.

Observed controls:

    saved issues are loaded through Issue.visible;

    new-issue maps require add_issues;

    project workflow screens call Redmine authorization;

    administration controllers require an administrator;

    invalid values are generally intersected with server-built objects.

No confirmed anonymous authorization bypass was found.

Residual concern:

    regression risk from callback ordering in patched Redmine controllers;

    future core changes may invalidate assumptions.

Normal authenticated Redmine user

Realistic attempts:

    request workflow maps for issues they cannot view;

    request project workflow configuration without permission;

    substitute another project, tracker, or role;

    submit write routes directly despite hidden UI controls.

Observed controls:

    issue visibility is enforced;

    project configuration routes authorize against the path project;

    tracker and role IDs are selected from project-derived lists;

    UI hiding is not used as the only authorization control.

No confirmed IDOR was found.
Project member

A project member may attempt to:

    read workflows for roles they do not hold;

    enable or clear workflow scopes;

    alter another project’s workflow;

    exploit an inherited workflow screen by directly submitting a write.

Observed controls:

    read and manage permissions are separate;

    manage permission requires membership;

    writes while inheriting are explicitly refused;

    project comes from the route rather than the payload.

The graph intentionally permits users with view_project_workflow to inspect other visible project roles. This is a policy decision, not a bypass.
Project manager

A manager granted manage_project_workflow can make high-impact configuration changes affecting every issue in the project. This is intended authority, but it deserves:

    strong audit visibility;

    concurrency protection;

    clear warning for empty workflows;

    regression tests proving it cannot affect other projects or generic rules.

The existing safe logging and project scoping are good controls.
Redmine administrator

An administrator can legitimately:

    change generic workflow behavior;

    apply changes to all projects;

    copy workflow populations;

    run migrations and destructive uninstall.

A compromised or mistaken administrator can cause significant availability and authorization changes. The current synchronous bulk operations amplify this risk. Administrator status should not be treated as a reason to omit transaction limits, stale-write detection, or durable audit records.
Malicious or compromised external service

No external service is consumed. This actor is not currently applicable.

A compromised gem release or GitHub Action remains a supply-chain actor:

    GitHub Actions permissions are read-only, which limits CI token impact.

    the unconstrained Deface dependency remains the primary runtime supply-chain concern.

6. Upgrade and Deployment Risks
Installation

    The plugin changes Redmine’s core workflows table.

    Adding the MySQL/MariaDB foreign key may rebuild the table and require an operational maintenance window.

    Deface is mandatory; dependency failure can stop initialization.

    Production installation must explicitly set RAILS_ENV=production; the documentation correctly warns that omission migrates the wrong database.

Migration

    Migration 004 backfills scopes from existing project-specific rules using set-based SQL. This is efficient but should be rehearsed on a production clone.

    Index creation and foreign keys can lock or rebuild workflows.

    The compatibility matrix excludes SQLite and unlisted Redmine minor releases.

Production deployment

    The README explicitly says not to use the plugin in production.

    Generic concurrent-save integrity remains unresolved.

    Bulk all-project operations are synchronous.

    Patch conflicts may be load-order dependent.

    No safe degraded mode exists if a required override or patch becomes incompatible.

Redmine upgrades

    Unknown Redmine minors are permitted to boot.

    Core-method digest tests skip versions absent from the known table.

    Deface anchors and semantics must be revalidated.

    Rails autoloading, callback ordering, helper-chain behavior, and private method signatures are upgrade-sensitive.

Plugin upgrades

    Core table migrations must be executed in the correct environment.

    Backfilled scope semantics differ from earlier implicit behavior only where direct database manipulation created rule rows without scopes; this is documented.

    A versioned upgrade compatibility test should run from every supported prior plugin release.

Rollback

    Rollback destroys all project-specific workflow rules before dropping project_id.

    This is logically necessary to prevent those rows from becoming generic, but it is irreversible without a backup.

    Rollback should be treated as a data migration, not a routine code rollback.

Uninstall

    Removing the directory without reversing migrations leaves invisible project rules in the core table, which reactivate if the plugin is reinstalled.

    A missing plugin directory may also make plugin migration reversal harder because migration code is no longer present.

    The uninstall procedure should be scripted and backup-verified.

7. Simplification Opportunities
Simplification 1: Reduce core administration view transformation

Current complexity

The plugin uses fifteen Deface overrides and patches core workflow controllers/helpers to support project selection, scope panels, bulk behavior, inventory links, hidden fields, and copy controls.

Simpler approach

Move project-specific administration to plugin-owned controllers and views, leaving Redmine’s generic workflow administration as close to core as possible.

A plugin-owned administration page can still reuse Redmine helpers where stable, but should own its form structure and routes.

Why safer

    fewer fragile view anchors;

    fewer conflicts with other plugins;

    easier authorization reasoning;

    easier system testing;

    clearer support boundaries between generic and project workflows.

Affected components

    lib/redmine_project_workflows/overrides/*

    lib/redmine_project_workflows/patches/workflows_controller_*

    lib/redmine_project_workflows/patches/workflows_helper_patch.rb

    core-workflow-related views and controller specs.

Simplification 2: Centralize compatibility policy

Current complexity

Compatibility knowledge is distributed across:

    init.rb comments;

    README;

    core digest service;

    YAML digest table;

    specs;

    Deface tests;

    CI matrix.

Simpler approach

Create one compatibility manifest listing:

    exact Redmine minor;

    Rails and Ruby range;

    supported databases;

    core method digests;

    Deface compatibility status.

Use it in:

    runtime diagnostics;

    CI;

    tests;

    documentation generation.

Why safer

It prevents the declared floor, documented support, tested versions, and runtime warnings from drifting independently.

Affected components

    init.rb

    README.md

    CoreMethodDigest

    core_method_digests.yml

    CI workflow

    plugin convention specs.

Simplification 3: Introduce one write-coordination abstraction

Current complexity

Concurrency handling is spread across:

    scope writer;

    matrix scope;

    transition writer;

    permission writer;

    copy patches;

    copy services.

Generic writes remain a special unprotected case.

Simpler approach

Introduce one small WorkflowWriteLock service with deterministic lock keys:

(rule_type, project-or-generic, tracker_id, role_id)

Every writer and copy operation acquires those keys before modifying rules.

Why safer

    one concurrency policy;

    less duplicated locking commentary and reasoning;

    generic and project writes behave consistently;

    easier concurrency testing.

Affected components

    MatrixScope

    ScopeWriter

    TransitionWriter

    PermissionWriter

    workflow copy services and patches

    concurrency specs

    one new lock table migration if that implementation is chosen.

Simplification 4: Reconsider the custom graph layout scope

Current complexity

The graph feature includes query, ranking, layout, extent, and text-fitting services plus SVG views and accessibility fallbacks.

Simpler approach

Options, in increasing scope:

    keep only the accessible transition table for the production milestone;

    use a simpler deterministic layered layout;

    make diagram rendering an optional module with an explicit size ceiling.

Why safer

    substantially smaller visual algorithm surface;

    fewer edge-routing and browser compatibility defects;

    lower response-generation cost;

    lets production hardening focus on workflow authorization and integrity.

Affected components

    graph query/layout/ranking/extent/text services;

    graph helpers and views;

    graph specs and controller action.

This is a product-scope recommendation, not a claim that the present graph code is defective.
Simplification 5: Replace repair-only duplicate handling with prevention

Current complexity

The plugin documents a manual deduplication rake task and distinguishes exact duplicates from contradictory rows.

Simpler approach

Serialize writes so duplicates cannot be produced by supported application paths. Retain the task only for preexisting or manually introduced corruption.

Why safer

Prevention gives operators deterministic results; repair after the fact cannot reconstruct intent.

Affected components

    workflow writers;

    lock service;

    deduplication task documentation;

    concurrency tests.

10. Final Decision
Would I personally approve this plugin for deployment on a production Redmine instance today?

No.

I would not approve it because the repository explicitly marks it alpha and warns against production use, generic concurrent workflow writes can still leave duplicate database rows, and the plugin’s large set of copied Redmine methods and Deface overrides can run on unverified future Redmine minors without a hard or administrator-visible safety boundary.

This is not a rejection of the underlying design. The explicit scope model, project isolation, authorization discipline, database foreign keys, payload whitelisting, audit-conscious logging, and test strategy are all strong. The plugin appears suitable for controlled staging or pilot use on an exact tested Redmine/database combination with backups and active maintainers.

For production approval, however, workflow correctness is authorization correctness. Silent version drift and unresolved concurrent generic writes are too consequential to accept.
